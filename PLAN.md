# revlog — план переписывания Logisim на современный стек

Статус: черновик архитектуры, git ещё не подключён. Документ фиксирует принятые
решения и объяснения к ним, чтобы не передумывать каждый раз заново.

## 0. Цель и рамки

Logisim (Java) — редактор схем + событийный симулятор цифровой логики
(вентили, шины, подсхемы как компоненты, память, таймдиаграммы). Переписываем
с нуля на современный стек, сохраняя суть: редактор схем + симулятор + плагины
+ headless-режим + возможность собрать десктоп-приложение.

Важно: оригинальный Logisim (и Logisim-evolution) под GPL. Переписывание —
clean-room: проектируем архитектуру и модель данных заново, не копируя код
и не портируя классы 1:1. Формат файлов тоже будет свой (см. §4), не .circ/XML.

## 1. Общая архитектура (слои)

```
┌────────────────────────────────────────────┐
│ UI Shell — Vue 3 + TypeScript               │  меню, палитра компонентов,
│                                              │  инспектор свойств, файлы,
│                                              │  настройки, диалоги
├──────────────────────────────────────────────┤
│ Editor Core — чистый TS/JS (без Vue)        │  сцена схемы, canvas-рендер,
│                                              │  hit-testing, drag/wiring,
│                                              │  undo/redo, сериализация
├──────────────────────────────────────────────┤
│ Engine Bridge — тонкий TS-слой               │  компиляция схемы → netlist IR,
│                                              │  батчинг вызовов в WASM,
│                                              │  чтение состояния пинов
├──────────────────────────────────────────────┤
│ Simulation Engine — Rust                     │  событийный планировщик,
│  → wasm32 (браузер)                          │  компонентная модель,
│  → native (CLI/тесты/Tauri)                  │  плагины через общий ABI
└────────────────────────────────────────────┘
```

Ключевая идея, которая объясняет пункты 2–4 разом: **движок ничего не знает
про UI**, а Editor Core ничего не знает про WASM-детали — он говорит с
движком через Engine Bridge, у которого есть заглушка (mock) для тестов
редактора без запуска симулятора. Это разделение — то, что делает headless-
режим (п.4) не отдельной фичей, а естественным следствием архитектуры, а не
доп. работой.

## 2. UI: Vue + TypeScript (shell) / чистый TS (редактор схем)

Решение подтверждаю — это правильное разделение, аналог того, как устроены
Excalidraw/tldraw/Figma: canvas-редактор с интенсивным взаимодействием
(перетаскивание, рисование проводов, hit-testing на каждый mousemove) плохо
уживается с реактивностью Vue — лишние ре-рендеры и накладные расходы на
отслеживание зависимостей там, где нужен прямой императивный контроль над
кадром. Vue хорош для "обычного" UI: панели, диалоги, инспектор свойств,
которые меняются редко и по явным событиям.

- Editor Core — chërный TS, свой scene graph, свой render loop на Canvas2D
  (не SVG — деградирует на схемах с тысячами элементов; не WebGL — оверкилл
  для 2D-схемотехники, усложнение без реальной необходимости).
- Пространственный индекс (grid/quadtree) для hit-testing и viewport culling
  на больших схемах — иначе даже быстрый движок симуляции упрётся в тормоза
  рендера.
- Editor Core экспортирует явный API (события: componentAdded, wireDrawn,
  selectionChanged...) — Vue-shell подписывается на него, а не наоборот.
  Editor Core не импортирует Vue вообще, что позволяет переиспользовать его
  без Vue (например, в тестах, или если позже понадобится другой UI-фреймворк).

## 3. Движок: Rust → WASM

Максимальная производительность и headless — по сути одно и то же решение,
не два отдельных. Обоснование Rust: cache-friendly data-oriented дизайн
(structure-of-arrays, компоненты и пины — целочисленные индексы, а не
объекты со ссылками), предсказуемая производительность без GC-пауз, и
единая кодовая база, которая компилируется в разные таргеты без переписывания
логики:

- `wasm32-unknown-unknown` + wasm-bindgen — для браузера.
- нативный таргет (rlib/binary) — для CLI, `cargo test`, встраивания в Tauri
  напрямую (десктоп-сборка вообще может не проходить через WASM — движок
  как обычный Rust-крейт, ещё быстрее).

### Модель симуляции
Сохраняем событийную (discrete-event) модель, как в оригинале, а не
"решать до стабилизации топологически" — она нужна, чтобы корректно
обрабатывать задержки распространения сигнала, генераторы/защёлки с обратной
связью и обнаружение осцилляций. Планировщик — очередь событий по времени
(min-heap), компоненты — плоские массивы, "грязные" компоненты — очередь
индексов на пересчёт. Это прямое попадание в сильные стороны Rust
(cache locality, отсутствие указательной "паутины").

### Встроенные компоненты vs плагины
Базовые вентили/мультиплексоры/регистры/ALU/RAM — реализованы нативно прямо
в движке (не через WASM-в-WASM), чтобы не платить накладные расходы на самом
горячем пути. Плагин-компоненты — отдельные WASM-модули с тем же интерфейсом
(см. §5), но чуть медленнее из-за границы вызова — это нормально, это не
hot path большинства схем.

### Граница TS ↔ WASM
Гибридный подход: wasm-bindgen для "холодных" операций (загрузка схемы,
регистрация плагина, редкие вызовы) — там важна эргономика, не скорость.
Для горячего пути (шаг симуляции, чтение состояния пинов) — свой протокол
поверх линейной памяти: движок пишет состояние в preallocated буфер,
JS читает его как `Uint8Array`/`DataView` без сериализации через
wasm-bindgen на каждый вызов. Один "тик" симуляции = один вызов в WASM,
а не вызов на каждое событие — иначе граница вызова съест весь выигрыш
от Rust.

### Воркер и потоки
Долгий/непрерывный запуск (свободно бегущие часы) стоит гонять в отдельном
Web Worker, чтобы не блокировать UI-поток редактора. Обмен состоянием —
через transferable ArrayBuffer каждый кадр, либо SharedArrayBuffer для
zero-copy — но это требует заголовков COOP/COEP на сервере, так что это
улучшение фазы 2+, не день 1 (флагирую как риск/зависимость от деплоя).

### Четырёхзначная логика (`Bit`) — сверено с `logisim-port`, не по памяти

Реализовано: `crates/plugin-abi` (`Bit`), `crates/engine/src/components.rs`
(вентили), `crates/engine/src/netlist.rs`+`sim.rs` (связность/распространение).

Каждый бит — не 0/1, а одно из четырёх значений, как в оригинальном
Logisim (`logisim-port/.../data/Value.java`, сверено с исходником напрямую,
не по памяти): `Zero`/`One` (зелёный), `Unknown` (синий — ничего не
драйвит эту точку), `Error` (красный — короткое замыкание, два и более
несогласных драйвера). Это не второстепенная деталь: без неё нельзя
корректно импортировать `.circ`-схемы, которые полагаются на floating-input
или на обнаружение короткого замыкания (§9).

Прямые следствия для модели связности:
- **Вход может иметь несколько драйверов**, не один — `input_sources` в
  `Netlist` это `Vec<BitRef>` на каждый *бит* каждого входа (`BitRef`,
  появился вместе со `Splitter`, §9 ниже), не `Option<PinRef>`. Значение
  бита — `fold(Bit::Unknown, Bit::combine)` по всем текущим драйверам этой
  битовой линии (`Value.combine` в оригинале: `Unknown` — нейтральный
  элемент, согласные значения проходят насквозь, несогласные дают `Error`).
- **Вентили `and`/`or`/`not` реализуют реальные таблицы истинности
  Logisim**, а не naive "трактовать не-1 как 0": `Zero` доминирует в `and`
  (короткое замыкание/неопределённость на одном входе не мешает другому
  входу принудительно занулить AND), `One` доминирует в `or`, симметрично;
  сверено построчно с `Value.java`/`GateFunctions.java`, не переизобретено.
- Непровязанный вход читается как `Unknown`, не `Zero` — иначе floating
  input на AND-гейте тихо превращался бы в "0", а не в неопределённость.

### Подтягивающий резистор (`PullResistor`) — отдельное правило свёртки

Добавлен сразу вместе с 4-значной логикой, а не отложен: его семантика
специально проверена по `logisim-port` (`CircuitWires.getThreadValue`/
`pullValue`, не придумана) и **явно не укладывается** в обычный
`Bit::combine` — обычная свёртка дала бы `Error` там, где резистор должен
молча проиграть реальному драйверу.

Правило (`sim.rs::gather_inputs`, двухфазно): сначала `combine` только
"настоящих" драйверов (без резисторов) → `real`; резисторы сворачиваются
`combine`'ом отдельно → `pull`. Итог — `real`, если `real != Unknown`
(резистор не участвует вообще, даже если `real` — это `Error` от короткого
замыкания настоящих драйверов); иначе — `pull`. То есть резистор побеждает
только когда точку буквально никто не драйвит — не сглаживает конфликт и не
может "перебить" единственный реальный источник, даже слабо определённый.
Резистор может тянуть и к `Error` (`X` в оригинале, третья опция атрибута
`ATTR_PULL_TYPE`) — не только к 0/1, это осознанная возможность оригинала
("эта точка не должна оставаться неподключённой"), не наша выдумка.

Реализация: `Gate::PullResistor { to: Bit }` — 0 входов, 1 выход, `eval`
константно отдаёт `to` (соответствует `propagate()` оригинала, который
буквально пустой — резистор не участвует в обычном распространении сигнала,
только в разрешении точки). Подключается в netlist как обычный драйвер;
особое поведение целиком в `gather_inputs`, не в самом компоненте.

## 4. Headless-режим (запуск без UI)

Не отдельная фича, а следствие §3: раз движок — чистый Rust-крейт без
знания о DOM, он одинаково доступен как:

- нативный CLI-бинарь (`engine-cli`) — прогнать схему с вектором входов,
  получить трассу выходов, без браузера вообще;
- WASM-модуль из Node.js — тот же движок, что в браузере, без UI;
- библиотека, встраиваемая в другой Rust-код (например, в тестовый раннер
  или в будущем бэкенд).

Это же прямо закрывает часть п.7 (тестирование) — самый быстрый цикл
обратной связи это `cargo test` без браузера и без WASM-прослойки вообще.

## 5. Система плагинов: WASM-only логика, JS — только для UI-надстроек

Разделяю плагины на два принципиально разных слоя вместо единого решения
"или JS, или WASM" — потому что у логических (симуляционных) плагинов и
у UI-плагинов разные требования:

**Логика (поведение компонентов) — только WASM.**
Причина: движок должен одинаково работать в браузере, в native CLI и в
тестах (§4). Если разрешить компонентам-плагинам логику на JS, headless/
native запуск либо теряет эти компоненты, либо требует тащить в native-
бинарь встроенный JS-движок (толсто, медленно, лишняя поверхность атаки).
WASM-плагин пишется на чём угодно (Rust, C, AssemblyScript, TinyGo) — язык
не важен, важен общий ABI (`init`, `eval(inputs) -> outputs`,
`pin_count`, `serialize_state`) — тот же контракт, что и у встроенных
компонентов внутри движка, то есть мы не изобретаем второй интерфейс.
Загрузку плагинного WASM-модуля делает хост (в браузере — JS через
`WebAssembly.instantiate`, в native — `wasmtime`/`wasmer` в CLI/Tauri), а не
сам движок изнутри себя — WASM-модуль не может сам инстанцировать другой
WASM-модуль без посредника-хоста, это техническое ограничение, которое надо
учитывать в реализации, а не только в теории.
Сэндбоксинг — бонус, а не только приём производительности: WASM
изолирован по памяти по построению, что важно, если плагины сторонние.

**UI/тулинг (кастомные property-панели, импорт/экспорт форматов, пункты
меню, темы) — JS/TS, опционально Vue-компоненты.**
Причина обратная: этому слою не нужно работать headless, зато нужна
хорошая DX (без шага компиляции, мгновенная перезагрузка, прямой доступ к
DOM/Vue). Риск встроенного JS-плагина, ломающего UI-поток — приемлем, т.к.
UI и так однопоточный/браузерный контекст; при необходимости позже можно
изолировать через Worker/iframe (по модели VS Code extension host), но это
не блокер для первой версии.

Итог: два ABI, а не один компромиссный — логика везде одинаково быстрая
и портируемая, UI-расширения максимально удобны для авторов. Это тот пункт
плана, который стоит явно обсудить перед реализацией — если вы хотите
разрешить JS и для логики компонентов (например, для простых учебных
компонентов), это возможно, но тогда придётся решать вопрос native/headless
отдельно (встраивать QuickJS-в-WASM для CLI — дорого и по сложности, и по
рантайму).

### Actions/readouts — интерактивные компоненты в ABI

Расширение базового контракта (`init`/`eval`/`pin_count`/`serialize_state`),
нужное для скриптовых тестов схем (§7): формализация того, что в оригинальном
Logisim и так есть неявно — **Poke tool** (клик по свитчу переключает его,
по кнопке — жмёт, пока зажата мышь). Один и тот же ABI для встроенных и
WASM-плагинных компонентов, как и остальной контракт:

- `actions() -> [ActionName]` + `invoke(name, arg?)` — "записывающие" методы
  с побочным эффектом на внутреннее состояние компонента (`on`/`off`/
  `toggle`/`set(v)`/`press`/`release`). Семантика — за реализацией
  конкретного компонента, не общая для всех (кнопка "жмётся", свитч
  "переключается" — разное поведение за одинаковым по форме вызовом).
- `readouts() -> [ReadoutName]` + `read(name) -> Value` — **без побочных
  эффектов**; важно, что `assert` в тестовом скрипте гарантированно ничего
  не меняет в схеме. Значение может быть осмысленно декодировано
  (7-сегментный индикатор отдаёт цифру, а не сырой бит-вектор), а не
  обязано быть сырым состоянием пина.

Отдельная от пинов система: `actions`/`readouts` — интерфейс для теста/
интерактивности, `pin`/`eval` — интерфейс для симуляции. Не всегда
взаимозаменимо (у кнопки нет "входного" пина вообще, только `press`/
`release`; у регистра `set(v)` — прямая запись состояния в обход
симуляции, полезно для тестового сетапа, но не то же самое, что подать
сигнал на вход).

## 6. Упаковка: Tauri вместо Electron/NW.js (рекомендация)

Раз движок уже на Rust, Tauri — не просто "аналог Electron на Rust", а
прямая синергия: десктоп-бэкенд Tauri может линковать движок как обычный
Rust-крейт напрямую, вообще без WASM-границы — то есть десктопная сборка
потенциально быстрее веб-сборки, и это без дублирования кода (тот же крейт,
просто другой feature-флаг таргета).

Дополнительно: заметно меньший размер бинарника (единицы МБ против
100+ МБ у Electron, т.к. Tauri использует системный WebView, а не тащит
Chromium), меньше потребление памяти. Минус — системный WebView
(WebView2/WebKit/GTK-WebKit) даёт чуть больше расхождений в рендере между
платформами, чем гарантированно одинаковый Chromium в Electron; это
компромисс, на который стоит пойти, но явно закладываю как риск ниже.

NW.js не рекомендую рассматривать отдельно от Electron — те же минусы
(бандл Chromium+Node), но менее развитая экосистема и поддержка; если
Tauri по какой-то причине не подойдёт (нужны specific Node-only API,
экосистема электрон-плагинов), fallback — Electron, а не NW.js.

## 7. Тестирование

Базовая, но многослойная система, использующая headless-движок как основу:

- **Rust/engine**: `cargo test` — юнит-тесты компонентов, интеграционные
  тесты полных схем; `proptest` для проверки арифметических компонентов
  (сумматор, ALU) на случайных входах; golden-тесты — схема + вектор входов
  + ожидаемая трасса выходов, гоняются через native CLI в CI без браузера
  вообще (самый дешёвый и быстрый уровень тестирования).
- **WASM-граница**: `wasm-bindgen-test` — по минимуму, т.к. сам bridge-слой
  должен быть тонким (вся логика — в чистом Rust-крейте, который уже
  покрыт тестами выше).
- **TS/редактор**: Vitest для чистой TS-логики Editor Core (геометрия,
  hit-testing, undo/redo, сериализация схемы) — без браузера, быстро.
- **Vue-shell**: Vue Test Utils / Testing Library — точечно, для панелей.
- **e2e**: Playwright — нарисовать схему, запустить симуляцию в браузере,
  проверить результат/визуальный снапшот.
- **Импортёр `.circ`**: отдельный пласт golden-тестов на реальных
  `.circ`-файлах (из оригинального Logisim/Logisim-evolution, не только
  синтетических) — сверяем и результат импорта (структура схемы), и
  поведение при симуляции после импорта. Реальные файлы полезнее
  синтетических здесь, т.к. ловят расхождения семантики, которые вручную
  придумать сложно.
- CI: после появления git — прогонять `cargo test` + wasm build +
  `vitest` + Playwright на каждый push. Пока репозитория нет, это пункт
  "день 1 после git init", не блокер плана.

### Скриптовые тесты схем (`.ctest`) — одна инфраструктура, две аудитории

Небольшой закрытый DSL поверх `actions`/`readouts` из §5, для сценариев вида
"выставить входы → просимулировать → проверить выходы". Не отдельная фича —
**тот же механизм**, что и golden-тесты движка/импортёра выше, только с
человекочитаемым текстовым синтаксисом вместо структуры данных в коде;
golden-тесты можно постепенно переписать в этом формате, а не поддерживать
два параллельных.

Два адресата одного и того же инструмента:
1. **Внутренние golden-тесты** — движок, встроенная библиотека компонентов,
   `.circ`-импортёр (замена/дополнение к тестам из пунктов выше).
2. **Студенческие схемы** — пользователь размечает в UI, каким компонентам
   присвоить `id` (см. §9 — тот же `ComponentInstance.id`, user-facing, не
   отдельная сущность), и пишет тест на свою схему тем же синтаксисом.
   Потенциально основа для автоматической проверки учебных заданий
   (контекст: `logisim-port/` уже содержит студенческие cdm-16 схемы) — не
   проектирую это отдельно сейчас, но держу в уме как причину следующего
   пункта.

Синтаксис:
```
component[sw_a] -> on
component[sw_b] -> set(0x05)
simulate
assert component[out] -> get == 0x08
```

Зафиксированные решения по грамматике:
- `simulate` без аргумента — прогон до квиесценции (устаканивание
  комбинационной логики и цепей обратной связи); `simulate <n>` — n тактов
  *общего* счётчика тактов (`Simulation::tick`, §9/"Clock/Register") плюс
  settle после каждого. Независимых часов с разным временем в Logisim не
  бывает — только один счётчик и per-instance делители периода, так что
  здесь нет неоднозначности даже при нескольких `Clock` разной частоты.
- Литералы значений: `0x1F` (hex), `0b101` (bin), `42` (dec), `on`/`off`/
  `true`/`false` как алиасы для однобитных сигналов.
- `#` — комментарий до конца строки.
- Несколько `assert` в одном скрипте; упавший `assert` не останавливает
  выполнение остальных — собираем все неудачи разом, а не только первую
  (важно для фидбека, не только для факта "тест не прошёл").
- Путь к файлу схемы — аргумент CLI (`engine-cli test project.json
  script.ctest`), не часть самого скрипта — скрипт остаётся переносимым
  между копиями/версиями схемы.
- Специально **не Turing-complete** (без циклов, без произвольного кода) —
  осознанное решение по безопасности (§12): если скрипты со временем станут
  частью автоматической проверки чужих (студенческих) работ, их должно быть
  безопасно исполнять без песочницы уровня плагинов.

**Реализовано**: `crates/engine/src/ctest.rs` (парсер + интерпретатор,
строчный, без внешних зависимостей) + `engine-cli test <project.json>
<script.ctest>`. Разрешение `component[id]` идёт через
`flatten_with_entry_map` (§9) — тот же маппинг, что и headless-отчёт.
Подтверждено на реальном скрипте: несколько провалившихся `assert` в одном
файле репортятся все разом, а не только первый; неизвестный `id` —
такая же собираемая ошибка, а не паника. `simulate <n>` теперь означает
`n` вызовов `Simulation::tick()` (общий счётчик тактов), каждый с settle
после — см. "`Clock`/`Register`" в §9 для полной модели и найденного по
пути реального бага с порядком первичного планирования гейтов.

## 9. Формат файлов и модель данных

- Формат — версионированный JSON (`schemaVersion`), не XML/.circ: проще
  парсить и в TS, и в Rust, читаемее для будущих плагинов/скриптов.
- Источник истины — **визуальная схема** (позиции компонентов, точки
  проводов, конфигурация) — то, что сохраняется на диск. **Netlist IR**
  (плоский граф для движка) — производный, эфемерный артефакт компиляции,
  никогда не сохраняется, как байткод относительно исходника. Это разделение
  важно держать явным, иначе легко скатиться в сохранение "скомпилированного"
  состояния и потерять возможность просто отредактировать схему текстом.
- Подсхемы (иерархический дизайн) — компонент типа "instance of circuit N",
  как в оригинале; резолвится в netlist на этапе компиляции.

### Черновая JSON-схема (конверт) — Фаза 1

Реализовано: `crates/engine/src/file_format.rs` (source of truth, с serde) +
зеркальный `packages/editor-core/src/file-format.ts` (синхронизируется
руками, пока расхождение не станет болезненным — тогда стоит вернуться и
рассмотреть кодоген из одного источника).

Сознательно описан только **конверт** — структура файла (circuit → components
+ wires + annotations), а не то, какие типы компонентов существуют и какие у
них атрибуты. `type` и `attrs` на этом уровне непрозрачны (`type: String`,
`attrs: BTreeMap<String, JsonValue>`). Это не недосмотр: если сейчас
перечислить конкретные типы (AND/OR/Mux/Register/...) прямо в файловой схеме,
схема незаметно срастётся с API стандартной библиотеки компонентов — а её мы
спроектируем в Фазе 2, когда будет ясно, как выглядит `Component`-трейт в
движке. Схему файла придётся тогда либо переделывать, либо она будет тянуть
за собой промежуточные, поспешные решения. Библиотека компонентов — забота
каждой их реализации (какие атрибуты у AND-гейта решает код AND-гейта), не
общего конверта.

Что зафиксировано на уровне конверта (осознанные решения, не производные от
библиотеки компонентов):
- **Адресация типов** — `"core:AndGate"` / `"core:circuit/<name>"` (подсхема)
  / `"plugin:<plugin-id>/<component-id>"`. Это схема адресации (namespacing),
  а не перечень существующих типов — годится уже сейчас, не блокирует
  библиотеку компонентов и сразу задаёт единый способ ссылаться и на
  встроенные, и на плагинные компоненты (см. §5/§13).
- **Ориентация — `facing` (east/west/north/south), не угол поворота** —
  повторяет модель самого Logisim; нужно для точного воспроизведения
  семантики при импорте `.circ` (см. ниже), а не общая абстракция "на
  будущее".
- **Провода — двухточечные сегменты** (`from`/`to`), как в `.circ`; узлы
  (junctions) неявные, по совпадающим концам. Тоже прямое следствие
  требования совместимости с импортом, не произвольный выбор.
- **Аннотации (текстовые метки) — отдельная сущность**, не `components`: у
  них нет пинов, они никогда не попадают в netlist.
- id — строки, не числа: стабильнее при правках, читаемее в git diff,
  совпадает с адресацией компонентов/плагинов.

Не входит в этот черновик (сознательно отложено): конкретные значения
`core:*` (Фаза 2), контракт манифеста плагина внутри `attrs`/скоупа проекта
(§5/§13 уже описывают модель на уровне ABI, но не то, как именно плагинная
зависимость фиксируется в файле — уточнится вместе с ABI), экспорт JSON →
`.circ` (не в скоупе, см. ниже), формальная валидация (JSON Schema/ajv) —
пока двух синхронизированных наборов типов (Rust/TS) достаточно, добавлять
третий артефакт истины преждевременно.

### Компилятор JSON → Netlist — Фаза 2.7 (начато)

Реализовано: `crates/engine/src/compile.rs` (`ProjectFile` → `HashMap<String,
CircuitTemplate>`, через `netlist::flatten`/`flatten_with_entry_map`),
подключено к `engine-cli` — headless-запуск реального `.json`-файла со
схемы до отчёта по значениям пинов теперь работает целиком.

- **Связность — по совпадению координат**, как в `.circ`: у каждого типа
  компонента фиксированная (пока небольшая и условная — своя, не
  повторяющая пиксельную геометрию `.circ`, это отдельная забота
  `.circ`-импортёра) геометрия пинов относительно `x`/`y`, с поворотом по
  `facing`; провода и пины объединяются в "сети" через union-find по точкам
  (совпадающие координаты — уже связаны, явный `WireSegment` для этого
  не обязателен). Каждая сеть → все pairs (выход × вход) в
  `CircuitTemplate.connections` — короткое замыкание и `PullResistor` от
  этого не отличаются, они уже поддержаны на уровне `Bit::combine`.
- **Порты подсхемы — те же `InputPin`/`OutputPin`-компоненты**, что видны
  и в самой схеме (сортировка по `id` даёт детерминированный порядок).
  Обнаружился реальный баг на стыке с уже существующим wire-elision-ом
  (§3/netlist.rs): материализованный `InputPin`-маркер порта продолжал
  участвовать в собственной внутренней разводке *даже когда схема
  используется как вложенная подсхема* — то есть вход AND-гейта получал
  одновременно и настоящее значение снаружи (через elision), и дефолтный
  `Zero` от самого маркера, что читалось как `Error` (ложное короткое
  замыкание). Исправлено добавлением `CircuitTemplate.port_marker_nodes` +
  флага `is_entry` в `netlist::expand`: связи узла-маркера учитываются,
  только когда схема — точка входа `flatten()`, а не вложенный инстанс.
  Известное ограничение, оставленное как есть (не блокер): у вложенного
  инстанса такой маркер остаётся адресуемым гейтом, но не отражает живое
  значение с границы — актуально для будущей адресации `.ctest`
  (`component[id]`) внутрь конкретного инстанса подсхемы, не для самой
  симуляции (она корректна).
- **`output_ports` в `netlist.rs` сделан симметричным `input_ports`**
  (`Vec<Vec<Vec<BitRef>>>` — порт, бит, список источников; не один `PinRef`
  на порт) — тот же принцип, что и у `PullResistor`: точка с несколькими или
  нулём реальных драйверов внутри подсхемы должна доносить это наружу
  (`Unknown`/`Error`), а не терять информацию на границе, схлопывая к
  одному источнику. Третий уровень вложенности (по биту) появился вместе со
  `Splitter` (§9 ниже) — до него ширина порта не влияла на маршрутизацию.
- **`netlist::flatten_with_entry_map`** — помимо `Netlist`, отдаёт
  маппинг "локальный индекс узла верхней схемы → глобальный индекс гейта".
  Нужен не только для отчёта `engine-cli`, но и для будущего `.ctest`
  (`component[id]` резолвится в этот же глобальный индекс).
- **`engine-cli`** — реально читает `.json`, компилирует, симулирует
  (`run_to_quiescence`), печатает `id (type) = значение` для всех
  `InputPin`/`OutputPin` верхней схемы; однобуквенный формат значения
  (`0`/`1`/`x`/`E`) — тот же, что `Value.toString()` в `logisim-port`, не
  придуман заново. Управления входами через CLI пока нет (нужно для
  `.ctest`, следующий шаг).

### Библиотека вентилей — Фаза 2, расширена до дефолтного набора Logisim

Реализовано: `crates/engine/src/components.rs` (`Gate`), `netlist.rs`
(`TemplateNode`), `compile.rs`. Было (см. выше в этом документе, историческая
запись Фазы 2): And/Or/Not/InputPin/OutputPin/PullResistor, все однобитные,
And/Or жёстко на 2 входа. Теперь:

- **Добавлены**: Nand/Nor/Xor/Xnor/Buffer/Constant — тот же набор, что в
  `std/gates`/`std/wiring` `logisim-port`. Nand/Nor — не отдельная логика, а
  `Bit::and`/`or`-свёртка + `.not()` (так же устроено в самих `*Gate.java`).
  Xor/Xnor — `GateFunctions.computeExactlyOne` ("ровно один вход истинен"),
  это реальный дефолт Logisim при arity > 2 (`GateAttributes.xorBehave =
  XOR_ONE`), не наивная цепочка `xor` (которая для arity > 2 даёт другой
  ответ — see `xor_is_exactly_one_true_input_for_wider_arity` тест).
  Альтернативный режим `XOR_ODD` (цепочка `xor`, доступна как атрибут в
  Logisim) пока не смоделирован — оба режима совпадают для обычного
  2-входового случая, который покрывает подавляющее большинство схем; см.
  открытый вопрос ниже.
- **Многобитная ширина (`bits: u8`, атрибут JSON `"width"`, 1..=32)** — у
  всех вентилей и Pin'ов. Потолок 32 — не наша оценка, это
  `Value.MAX_WIDTH`/`BitWidth`'а собственный предел в `logisim-port`
  (`data/Value.java`, `data/BitWidth.java`), сверено построчно, не
  предположено. Значение вне 1..=32 — ошибка компиляции
  (`CompileError::InvalidWidth`), не молчаливое обрезание.
- **Переменная арность (`inputs: usize`, атрибут `"inputs"`, 2..=32)** — та
  же логика, что `GateAttributes.ATTR_INPUTS`/`MAX_INPUTS`; дефолт в нашей
  схеме — 2 (у самого Logisim в UI дефолт 5, но это UI-удобство, не
  требование корректности).
- **Многобитная логика — не отдельная реализация**: `Value.java`'s
  `and`/`or`/`xor`/`not` для ширины > 1 считают через битовые маски (`int`)
  ради скорости; расписав эту арифметику по битам, она оказывается
  математически тем же самым, что применение уже проверенных однобитных
  `Bit::and`/`or`/`xor`/`not` независимо к каждой позиции бита — у нас и так
  `Vec<Bit>`, так что `fold_bits`/`fold_xor_one` в `components.rs` делают
  именно это, без повторного вывода таблиц истинности.
- **`sim.rs::gather_inputs` обобщён с одного бита на шину**: раньше
  `Bit::combine`-свёртка нескольких драйверов одной точки брала только
  первый бит каждого сигнала (`signal.first()`) — работало, пока всё было
  однобитным. Теперь свёртка идёт по каждой позиции бита независимо, по
  ширине самого широкого реального драйвера на этой точке; более узкий
  драйвер на той же точке даёт `Unknown` на недостающих старших битах —
  тот же принцип, что `bit_at`/`Signal::get` в `components.rs`.
- **Атрибуты названы как в самом Logisim** (`"width"` = `StdAttr.WIDTH`,
  `"inputs"` = `GateAttributes.ATTR_INPUTS`, `"value"` = `Constant.
  ATTR_VALUE`, сверено в исходниках) — осознанный выбор: наша JSON-схема не
  обязана совпадать с `.circ`, но раз имена бесплатны, совпадение с
  Logisim снимает будущую работу у `.circ`-импортёра (Фаза 2.7).
- **`PullResistor` остаётся однобитным** — у настоящего Logisim он имеет
  `BitWidth.UNKNOWN` (ширина 0) и **автоматически** принимает ширину той
  сети, к которой подключён (`PullResistor.java`); у нас пока нет
  вывода ширины по сети (`compile.rs` знает ширину только из явного атрибута
  компонента, не из подключённых проводов) — оставлено как известное
  ограничение, не забыто. Подтяжка широкой шины пока требует по резистору
  на каждый бит отдельно.

### `Clock`/`Register` — один общий счётчик тактов, не независимые таймеры

Реализовано: `Gate::Clock`/`Gate::Register` (`components.rs`),
`TemplateNode::Clock`/`Register` (`netlist.rs`), `Simulation::tick`
(`sim.rs`), `"core:Clock"`/`"core:Register"` в `compile.rs`.

Пользователь верно предположил и попросил свериться с оригиналом, а не
угадывать: в `logisim-port` **нет** независимых тактовых генераторов.
Ровно один общий счётчик тиков на всю симуляцию (`Propagator.ticks`);
`Simulator.doTick()` увеличивает его и обходит **все** `Clock`-компоненты
по всей иерархии (`CircuitState.tick` → `Clock.tick`), включая вложенные
подсхемы. Каждый `Clock` — чистая функция этого общего счётчика и
собственных атрибутов-делителей `highDuration`/`lowDuration`:
`curValue = ticks % (high + low) < low` (плюс инверсия при нечётном числе
ручных Poke-кликов, `ClockState.clicks`), сверено построчно в `Clock.java`.
Порядок в `Simulator.java`: `doTick()` → `propagate()` в цикле до
стабилизации — "один логический тик" = один шаг общего счётчика + полный
settle.

- **`Simulation::tick()`** — увеличивает общий `global_ticks`, обновляет
  кэш `sending` у каждого `Gate::Clock` в netlist (список посчитан один
  раз в `Simulation::new`), планирует пересчёт изменившихся. Само
  распространение изменения — обычный `step()`/`run_to_quiescence()`,
  как и для любого другого внешнего воздействия (`invoke`). `eval()` у
  `Gate::Clock` **никогда** не пересчитывает `sending` сам — только
  отдаёт закэшированное значение (как `Clock.propagate()` в Java);
  пересчитывает исключительно `Gate::tick`.
- Это закрывает старый открытый вопрос §14 про "`simulate <n>` при
  нескольких независимых часах": независимых часов не существует, `n`
  однозначно означает "n раз: общий тик + settle" (`ctest::run`'s
  `Statement::Simulate` обновлён соответственно).
- **`Register`** (`std/memory/Register.java`, сверено построчно) — `D`,
  `CK`, `CLR`, `EN` входы (фиксированный порядок 0..4, ключ для
  `compile.rs::register_geometry`), edge/level-триггер по атрибуту
  `"trigger"` (`"rising"/"falling"/"high"/"low"`, дефолт `"rising"` — те
  же строки, что `StdAttr.TRIGGER`). Два нюанса, оба неочевидны и оба
  сверены с источником, а не додуманы: (1) `EN` разрешает защёлкивание
  при **любом** значении, кроме явного `Zero` (`state.getPort(EN) !=
  Value.FALSE`) — неподключённый/`Unknown` `EN` по умолчанию считается
  "включён", не "выключен"; (2) частично неопределённый `D` (любой бит
  `Unknown`/`Error`) отбрасывается целиком в этом такте — `value` не
  меняется вовсе, не защёлкивается "наполовину" (`in.isFullyDefined()`).
  `CLR` — асинхронный, побеждает без всякого фронта.

**Найденный и исправленный реальный баг** (не гипотетический — воспроизведён
через `engine-cli test` на `.ctest`-сценарии до фикса): `Simulation::new`
изначально планировала **все** гейты на один и тот же момент `t=0`. Для
комбинационной логики это безобидно — она не хранит историю, "протухшее"
первое чтение просто перекрывается более поздним правильным батчем, пока
`run_to_quiescence` не опустошит очередь. Но `Register.last_clock`
записывается безусловно на каждый `eval`, и если самое первое чтение `CK`
попадало на ещё не закоммиченный (`Unknown`-плейсхолдер) вывод `Clock` в
том же самом батче — этот `Unknown` **навсегда** портил историю фронта:
реальный переход `Zero → One` переставал засчитываться Rising-триггером
(`old == Zero` уже никогда не выполнялось). Юнит-тест на compile.rs это не
поймал случайно (там перед первым `tick()` стоял лишний `run_to_quiescence()`,
который случайно "самоисцелял" порчу); а вот естественный порядок вызовов
`.ctest`-скрипта (`simulate` первой строкой, без явного settle до неё) —
ловил стабильно.

Исправление — `sim.rs::priming_depths`: первичные события `t=0` заменены на
приоритет по глубине зависимостей от источников (relaxation/fixed-point по
`input_sources`, а не топологическая сортировка — в схеме бывают обратные
связи/защёлки, для них это честно и осознанно падает на `depth=0`, как у
обычного источника, дальнейшая стабилизация — как раньше, через обычный
re-trigger). Гарантирует: первый `eval` любого гейта видит только уже
закоммиченные (не плейсхолдерные) значения того, что его питает напрямую.
Регрессионный тест `sim::tests::
register_sees_the_first_real_clock_edge_even_without_a_leading_settle`
специально воспроизводит порядок вызовов `.ctest` (`tick()` до первого
settle) и проверен на то, что ловит баг (временный откат фикса — тест
красный).

### Multiplexer/Demultiplexer — реализовано; Splitter — сознательно отложен

Прежде чем гадать, что добавлять дальше в библиотеку, посмотрел на реальную
демо-схему 16-битного CPU из `logisim-port` (`doc/circs/cpu-16bit.circ`) —
это **не** cdm-16 (которого в репозитории нет вообще, студенческого проекта
не нашлось), просто эталонный пример посложнее синтетических тестов.
Подсчёт компонентов по файлу:

```
14 Splitter, 13 Multiplexer, 10 Register, 4 Demultiplexer, 4 Constant,
11 AND Gate, 7 NOT, 4 OR
```

`Splitter`/`Multiplexer` встречаются чаще большинства базовых гейтов — это
и определило приоритет, а не догадка.

**Реализовано**: `Gate::Mux`/`Gate::Demux` (`components/plexers.rs`),
`TemplateNode::Mux`/`Demux` (`netlist.rs`), `"core:Multiplexer"`/
`"core:Demultiplexer"` (`compile/plexers.rs`, новая категория наравне с
`logic`/`wiring`/`memory`). Сверено построчно с `Multiplexer.java`/
`Demultiplexer.java` (`std/plexers`):
- Оба избегают отдельной "enable"-логики: `en != Zero` включает (тот же
  идиом, что уже видели на `Register.EN`) — `Unknown` считается активным,
  не выключенным. Реальный конфликт драйверов (`Error`) — отдельная ветка,
  но без java-шной проверки `isPortConnected`: в нашем движке
  неподключённый пин и так резолвится в `Unknown` через
  `gather_inputs`-свёртку (§9), `Error` там в принципе не может возникнуть
  без реального подключения — проверка избыточна.
- Select декодируется трёхвариантно (`decode_select`, общий для обоих):
  любой бит `Error` → `Error` (даже если другие биты в порядке или
  `Unknown` — точный приоритет `Value.isErrorValue()`), иначе любой
  `Unknown` → `Unknown`, иначе — чистый индекс.
  Атрибут `"select"` (ширина селектора, 1..=5) и `"enable"`
  (bool, дефолт `true` — то есть Mux/Demux **по умолчанию** с
  enable-пином, не без него), `"disabled"` (`"Z"`/`"0"`, дефолт `"Z"` =
  floating) — имена и дефолты в точности как в `Plexers.java`.
- У Demux свой доп. атрибут `"tristate"` (дефолт `false`): чем "простаивают"
  невыбранные выходы — `Zero` или `Unknown`. Не путать с `"disabled"`
  (это про состояние en=0, а `tristate` — про обычный простой).
- Задержка обоих — `Plexers.DELAY = 3` (не 1, как у обычных гейтов).

**`Splitter` осознанно не делался вместе** — он требует адресации по
диапазону бит, а не целым пином, т.е. меняет базовую модель
`netlist::connections`. Реализован отдельным шагом ниже.

### `Splitter` — не компонент, а структурное сращивание проводов по битам

Ключевой факт, сверенный по `Splitter.java`/`CircuitWires.java`: в реальном
Logisim `Splitter` **не симулируется**. `Splitter.propagate()` — пустое тело
(`; // handled by CircuitWires, nothing to do`). Вся работа делается один раз
при перестройке схемы в `CircuitWires.java` — проход "unite threads going
through splitters" объединяет конкретный *бит* объединённого конца с
конкретным *битом* одного из отводов (`bit_end`/`bit_thread`, вычисленные в
`Splitter.configureComponent`). Это буквально сращивание проводов на уровне
отдельных битов, не гейт с направлением "вход → выход" — ток может течь в
любую сторону, и в отличие от Mux/Demux (у которых Java явно решает "кто
кого поборол"), тут решать нечего: это просто один и тот же электрический
узел под двумя разными именами.

Отсюда — архитектурное решение, а не просто новый вариант `Gate`:

- **Юнит связности стал битовой линией `(Point, bit)`, а не целым пином.**
  `netlist::PinRef` (`(node, pin)`) остался как был для мест, где пин
  адресуется целиком (например, `Simulation::output_of`), но появился
  `netlist::BitRef = (node, pin, bit)` — именно он теперь единица
  `CircuitTemplate::connections`/`input_ports`/`output_ports` и
  `Netlist::input_sources`/`fanout` (`[gate][pin][bit] -> Vec<BitRef>`).
  Обычная (не-`Splitter`) проводка тоже адресуется по битам — сознательно
  единое представление, а не "быстрый путь для целых пинов + отдельный
  случай для Splitter": бит `i` пина шириной `W` и так был электрически
  независим от бита `i+1`, `Splitter` просто первый компонент, которому это
  различие видно снаружи одного гейта.
- **`Splitter` не становится узлом (`TemplateNode`/`Gate`) вообще.**
  `compile_circuit` встречает `"core:Splitter"` до обычного
  `compile_leaf`-диспетчера и не кладёт его в `nodes` — компонент целиком
  потребляется на этапе построения union-find (`compile/splitter.rs`
  возвращает `SplitterWiring`, а не `(TemplateNode, Geometry)`). Это прямое
  отражение того, что в самом Logisim это не runtime-компонент. Следствие,
  которое едва не привело к багу: локальный индекс узла в `nodes` **больше
  не совпадает** с позицией компонента в JSON-массиве `Circuit::components`
  (Splitter съедает слот в массиве, но не в `nodes`). У `CircuitTemplate`
  появилось поле `component_index: HashMap<String, usize>` — реальное
  сопоставление `id → индекс узла`, а `engine-cli`
  (`resolver`/`run_report`) и всё, что раньше молча полагалось на "позиция
  в массиве == локальный индекс", теперь идёт через него.
- **Union-find обобщён до битовых линий.** Провод объединяет все 32 линии
  сразу в обеих точках (`Value.MAX_WIDTH` — верхняя граница, лишние
  никем не запрошенные линии просто не мешают); `Splitter` дополнительно
  сливает `(комбинированная_точка, i)` с `(точка_отвода[bit_end[i]-1],
  bit_thread[i])` для каждого `i`, где `bit_end[i] > 0` (0 = не подключено —
  такой бит остаётся плавающим/`Unknown`, не молчаливым нулём).
- **Ширина пина понадобилась до появления `Gate`.** `sim.rs::gather_inputs`
  должен собирать сигнал правильной *длины* даже для битов без единого
  драйвера (иначе, например, `Register.D.isFullyDefined()` увидит
  укороченное "слово" и ошибочно сочтёт его полностью определённым). Отсюда
  — `Gate::input_width`/`output_width` (по категориям, как и остальные
  inherent-методы) и зеркальные `TemplateNode::input_width`/`output_width`
  (нужны в `compile_circuit` до того, как `Gate` вообще существует).
  `Subcircuit`-у ширина порта неоткуда взяться из самого узла — она приходит
  из таблицы `port_widths`, которую `compile()` строит заранее по каждому
  `InputPin`/`OutputPin` каждой схемы (та же идея, что уже была у
  `port_counts`, только с шириной, а не только количеством).

Атрибуты — снова имена самого Logisim (`SplitterAttributes.java`):
`"incoming"` (`ATTR_WIDTH`, ширина объединённого конца, дефолт 2),
`"fanout"` (`ATTR_FANOUT`, 1..=32, дефолт 2). Единственное отступление —
`"bits"`: в реальном Logisim распределение по битам живёт в отдельных
Swing-атрибутах `bit0`, `bit1`, ... (`SplitterAttributes.BitOutAttribute`),
что осмысленно только для отдельного комбобокса на каждый бит; здесь это один
JSON-массив (индекс = бит объединённого конца, значение = номер отвода
1-based, `0` = не подключено) — тот же самый `bit_end`, просто без
Swing-ограничения. Без `"bits"` — дефолтное распределение
(`SplitterAttributes.computeDistribution`, `order = 1`): при `fanout >=
incoming` бит `i` уходит на отвод `i+1` (по одному биту на отвод); иначе —
смежные диапазоны по порядку, "лишние" от деления биты достаются первым
отводам. Формула перенесена построчно, включая правило переноса остатка.

Проверено (`compile/splitter.rs`'s tests): разбиение 8-битной шины на две
половины по умолчанию, обратная операция (два полубайта, сведённые через
объединённый конец — доказывает, что сращивание действительно
двунаправленное, а не переодетый Demux с фиксированным направлением), и
плавающий (не подключенный явным `"bits"`) бит. Плюс сквозной прогон через
`engine-cli test` на реальном JSON/`.ctest`.

### Adder/Subtractor/Comparator — расследование подозрения на переполнение

Перед реализацией пользователь специально попросил проверить, не работает
ли сложение в оригинальном `Adder.java` некорректно из-за переполнения при
сложении — разобрал `Adder.computeSum` построчно, с конкретным численным
трейсом, а не на глаз.

**Вывод: в самой Java нет бага.** `computeSum` считает по-разному в
зависимости от ширины:
- `w == 32`: собирает операнды в `long` (`(long) a.toIntValue() & mask`, где
  `mask = (1L << w) - 1`) — приведение `int → long` в Java **знаковое**
  (sign-extend), но последующий `& mask` в точности отменяет это
  расширение, корректно восстанавливая беззнаковое 32-битное значение.
  Дальше `sum = ax + bx + cx` в `long` не переполняется (максимум
  `2*(2^32-1)+1 < 2^33`, далеко до предела `long`), а `sum >> 32` (сдвиг
  `long` на 32 — это **не** UB в Java, в отличие от сдвига `int` на 32)
  корректно достаёт бит переноса.
- `w < 32`: `int sum = a.toIntValue() + b.toIntValue() + c_in.toIntValue()`
  — здесь при `w` близком к 31 сумма действительно может "перевалить" за
  `Integer.MAX_VALUE` и стать отрицательной с точки зрения знакового `int`.
  Но это **безопасно**: Java `int`-арифметика — это модульная (по `2^32`)
  арифметика по спецификации, и извлечение конкретного бита через
  `(sum >> w) & 1` корректно достаёт именно этот бит независимо от того,
  "ушла" сумма в отрицательные числа с точки зрения знака или нет — сдвиг
  вправо (что арифметический `>>`, что логический `>>>`) не портит более
  младшие биты, только к ним ничего не примешивает сверху. Проверено
  вручную на граничном случае `w=31`, `a=b=2^31-1`, `c_in=1`.

**Но это не значит, что тот же трюк безопасно переносить в Rust один в
один.** У Rust другая модель переполнения: арифметические операторы
паникуют в debug-сборке при переполнении (в отличие от всегда-молчаливого
wraparound в Java), а сама граница `w == 32` — именно то место, где `1u32
<< 32` уже UB/паника без явного спецкейса (тот же класс проблем, что уже
разбирался в `BitWidth.getMask()` при работе с `Value.MAX_WIDTH`). Поэтому
решение — **не** переносить трюк с нативными `u32`/`u64` вообще, а
реализовать сложение как поразрядную свёртку по `Bit`
(`components/arithmetic.rs::ripple_carry_add`), буквально копируя "не
полностью определённую" ветку `computeSum` (её собственный bit-serial
ripple-carry путь) и используя её **безусловно**, не только как fallback —
она математически эквивалентна быстрому пути при полностью определённых
операндах (таблица истинности полного сумматора — это и есть определение
двоичного сложения, не приближение к нему), так что от отказа от
быстрого пути ничего не теряется, а весь класс переполнений исчезает
вместе с отсутствием нативной целочисленной арифметики. Тот же принцип
"поразрядная свёртка по `Bit`, а не переизобретённая целочисленная
арифметика", что уже был у `logic.rs`'s многобитных гейтов.

Отдельно найдена и воспроизведена тонкость с плавающим переносом:
`computeSum` явно приводит `c_in == Unknown` к `Zero` **до** любых
вычислений (`if (c_in == UNKNOWN || c_in == NIL) c_in = FALSE`) — то есть
неподключённый `C_IN` у одиночного сумматора не "отравляет" всю сумму
неопределённостью (в отличие от, скажем, идиомы `EN != Zero` у `Register`).
У `Subtractor` это ещё тоньше: он делает **свою собственную** такую же
коррекцию для `B_IN` **перед** тем как инвертировать его (`b_in.not()`) и
передать в `computeSum` как перенос — если бы порядок был обратным (сначала
`.not()`, потом коррекция), результат был бы другим, потому что
однобитный `Value.not()`/`Bit::not` (уже сверено ранее) переводит `Unknown`
не обратно в `Unknown`, а в `Error` (`width <= 1` ветка `Value.not()`), что
без явной коррекции спереди отравило бы вычитание целиком.

**Реализовано**: `Gate::Adder`/`Subtractor`/`Comparator`
(`components/arithmetic.rs`), `TemplateNode`-аналоги (`netlist.rs`),
`"core:Adder"`/`"core:Subtractor"`/`"core:Comparator"`
(`compile/arithmetic.rs`, новая категория). `Subtractor` не дублирует
сложение — реализован как `in0 + ~in1 + ~b_in` через тот же
`ripple_carry_add`, один в один с `Subtractor.java`. `Comparator` сравнивает
побитово от старшего бита к младшему; атрибут `"mode"`
(`"twosComplement"`/`"unsigned"`, дефолт `"twosComplement"` — имя и дефолт
как в `Comparator.java`) влияет только на то, как читается несовпадение
именно на старшем бите (своп операндов в этой позиции — перенесено из
`Comparator.propagate` буквально). Задержки — `(width + 2)`/`(width + 4)`
тактов, `Adder.PER_DELAY`/своя константа `Subtractor`, сверено построчно.
Обратная совместимость: ни один существующий тип/атрибут/сигнатура не
менялись, только добавлены новые варианты `Gate`/`TemplateNode` и новая
категория `compile`/`components` — старые тесты (86 до этой фичи) прошли
без изменений.

Проверено (юнит-тесты `components/arithmetic.rs` + компиляционные тесты
`compile/arithmetic.rs`, включая явный тест на границе `w=32`) и сквозным
прогоном через `engine-cli test`.

### Multiplier/Divider — найдены реальные баги переполнения на границе w=32

Продолжение расследования выше — на этот раз баг **действительно нашёлся**,
только не в `Adder`, а в `Multiplier.java`/`Divider.java`. Оба разобраны
построчно с ручным численным трейсом (не "выглядит подозрительно", а
конкретные числа, посчитанные вручную и перепроверенные).

**`Multiplier.computeProduct`** (быстрый путь):
```java
long sum = (long) a.toIntValue() * (long) b.toIntValue() + (long) c_in.toIntValue();
```
В отличие от `Adder.computeSum`'s ветки `w>=32` (которая корректно делает
`(long) x & mask`, отменяя знаковое расширение), здесь **нет маскирования**
вообще. При `w=32` и операнде со старшим битом (например, `a=0x80000000`,
беззнаковое значение 2^31) `a.toIntValue()` возвращает Java `int` со знаком
-2147483648; `(long)` — это **знаковое** расширение (sign-extend), а не то
беззнаковое, что нужно. Трассировка: `a=2^31, b=2` → верный ответ:
низкое слово=0, высокое слово=1 (2^31×2=2^32 ровно). Java: `sum =
-2147483648L × 2L = -4294967296L`; низкое слово `(int)sum` **случайно**
совпадает с верным (0 — арифметика по модулю спасает низкие биты), но
высокое слово `(int)(sum >> 32)` = -1, что как беззнаковое 32-битное число
— `0xFFFFFFFF` вместо верного `1`. **Подтверждённый баг**, не гипотеза.

**`Divider.computeResult`** (быстрый путь) — тот же класс проблемы, другое
место:
```java
long num = ((long) upper.toIntValue() << w) | ((long) a.toIntValue() & 0xFFFFFFFFL);
```
`a` замаскирован (`& 0xFFFFFFFFL`) корректно, но `upper` (старшая половина
делимого) — **нет**. При `w=32`, `upper=0x80000000` (2^31), `a=1`: истинное
делимое (беззнаковое) = `2^63 + 1`. Битовый паттерн `num` после сдвига/OR
действительно корректен (`0x8000000000000000 | 1`), но дальше Java делит
его как **знаковый** `long` — а этот паттерн как знаковое число равен
`1 - 2^63` (глубоко отрицательное). Трассировка с конкретным `b=10`:
верный результат `922337203685477581` ост. `3`; Java (даже после своей же
коррекции отрицательного остатка `if (rem<0) {...}`) выдаёт
`-922337203685477581` ост. `7` — оба поля неверны, коррекция компенсирует
не полностью. **Подтверждённый баг**, не гипотеза.

Оба бага — одна и та же причина: `Value.toIntValue()` при `width=32`
возвращает Java `int`, который может быть отрицательным (полный 32-битный
паттерн), и `(long)`-каст **знаково** расширяет его, а не **нулём** — нужна
явная маска `& 0xFFFFFFFFL`, которую `Adder` (в своей ветке `w>=32`) и
`Divider` (только для `a`, не для `upper`!) проставили, а `Multiplier`
(нигде) и `Divider` (для `upper`) — нет.

**Решение**: не переносить баг "для совместимости" — Rust-реализация ведёт
себя правильно, без каких-либо исключений на границе `w=32`, потому что
`u32 → u64` в Rust — это **всегда** беззнаковое (zero-extending)
расширение, там просто нет знаковой ловушки, в которую можно случайно
попасть. `.circ`-совместимость (§9) — это совместимость по *поведению*
компонентов, не обязательство один-в-один воспроизводить артефакт
представления целых чисел в конкретном хост-языке, у которого никогда не
было аппаратного смысла.

**Реализовано**: `Gate::Multiplier`/`Divider` (`components/arithmetic.rs`),
`TemplateNode`-аналоги, `"core:Multiplier"`/`"core:Divider"`
(`compile/arithmetic.rs`). В отличие от `Adder`/`Subtractor`, у `C_IN`
(`Multiplier`) и `UPPER` (`Divider`) ширина **не 1 бит, а `width`** — это
не однобитный перенос, а полноценный второй операнд для сцепления
нескольких компонентов в более широкое умножение/деление (schoolbook
long-multiplication по "цифрам" шириной `width`, а не по битам). Плавающий
`C_IN`/`UPPER` коэрцируется в ноль **только если весь целиком
Unknown** (`Value.isUnknown()`'s собственное определение — "каждый бит
Unknown", не "хотя бы один"), в отличие от однобитного `C_IN` у `Adder`,
где эти два условия совпадают тривиально — отдельно проверено тестом
(`multiplier_partially_floating_carry_in_is_not_coerced_and_yields_unknown`).
Деление на ноль — не `Error`, а тихая подмена делителя на 1 (`Divider.
java`'s собственный, необычный выбор, воспроизведён буквально, не
"исправлен" — это не баг, это осознанная особенность оригинала).

Ветка "не полностью определён" у `Multiplier.computeProduct`
дополнительно реализует свою куда более тонкую эвристику (префиксное
"known"/"unknown"/"error" разбиение через `getKnown`/`findUnknown`/
`findError` — часть низких битов результата может быть точно известна,
даже если часть операнда ещё не устоялась). Сознательно **упрощено** здесь
до общего для `Multiplier`/`Divider`/`Comparator` правила: `Error` где
угодно → весь результат `Error`; иначе `Unknown` где угодно → весь
результат `Unknown`; иначе точное вычисление — сама эта эвристика в
оригинале приближённая, не аппаратная спецификация, а для `Divider`
(единственного из всей группы) это в точности то, что делает сам Java-код,
без всякого упрощения с нашей стороны.

Проверено юнит-тестами (`components/arithmetic.rs`, включая тесты,
воспроизводящие **именно** оба найденных сценария бага на границе `w=32` —
`multiplier_at_width_32_does_not_sign_extend_a_top_bit_set_operand`,
`divider_at_width_32_treats_the_dividend_as_unsigned_across_the_boundary`),
компиляционными тестами и сквозным прогоном через `engine-cli test`.
Обратная совместимость: 86 тестов до этой фичи не изменились, добавлены
только новые варианты `Gate`/`TemplateNode`.

### `Tunnel` — сращивание проводов по имени, найдено по частоте в реальном проекте пользователя

В отличие от прошлых шагов (арифметика — по частоте в демо-файле
`cpu-16bit.circ`), этот компонент выбран по анализу трёх настоящих `.circ`
пользователя (`demo-projects/`: `CdM-8-mark5-full.circ`, `main.circ`,
`project_workings.circ` — курсовой проект первого курса, процессор CdM-8 +
реализация игры "манкала"). Разбор XML показал `Tunnel` самым частым
компонентом вообще — 315 вхождений на три файла, при полном отсутствии
поддержки в движке. Без него ни один из этих файлов не собрался бы.

Как и `Splitter`, `Tunnel` — не симулируемый компонент:
`Tunnel.propagate()` в `logisim-port` — пустая заглушка ("nothing to do -
handled by circuit"). Настоящее сращивание — `CircuitWires.
connectTunnels()`: все экземпляры `Tunnel` в пределах *одной* схемы
группируются по значению атрибута `label` (`StdAttr.LABEL`, обрезанное
`trim()`; пустая строка — `if (!label.equals(""))` — вообще не участвует в
группировке, то есть безымянный туннель ни с чем не соединяется), и все
точки внутри одной группы объединяются в один `WireBundle` — ровно так же,
как если бы между ними шёл провод. Ширина берётся из фактически
подключённого провода (`StdAttr.WIDTH` тунеля — только для размера пина на
экране, не участвует в сращивании; проверено построчно по `Tunnel.java` и
`TunnelAttributes.java`).

В Rust-порте `Tunnel` отражён так же, как `Splitter` — не материализуется
ни в `TemplateNode`, ни в `Gate`; `compile_circuit` при встрече
`"core:Tunnel"` не создаёт узел, а копит `(label, точка)` в
`HashMap<String, Vec<Point>>`, и после обычного объединения проводов и
фьюзинга сплиттеров союзит все 32 битовые "дорожки" (`Lane`) между каждой
парой точек внутри одной непустой группы меток — тем же union-find, что и
обычные провода. Никакой отдельный модуль не понадобился (в отличие от
`Splitter`, у которого своя нетривиальная геометрия `bit_end`/`bit_thread`)
— это ~10 строк внутри `compile/mod.rs` плюс `tunnel_label()`.

Важный нюанс, который стоило проверить отдельно: `Tunnel`'s порт в Java —
`Port.INOUT` (`Tunnel.java`, `configureNewInstance`), т.е. это
двусторонняя точка, а не источник/приёмник. В Rust-реализации это
получилось "бесплатно" за счёт самого подхода — `Tunnel` не заводит узел и
не имеет входов/выходов вовсе, а просто отождествляет координаты через
union-find; направление потока целиком определяется потом, симметрично,
общим кодом сборки net'ов (кто угодно из группы может быть драйвером, кто
угодно — потребителем). Отдельным тестом (`tunnel_is_direction_agnostic`)
подтверждено, что результат не зависит от того, через какой из двух
одноимённых `Tunnel` физически подключён драйвер, а через какой —
потребитель.

Проверено тестами (`compile/mod.rs`):
`tunnel_connects_same_labeled_points_without_a_direct_wire` (все 4 бита
проходят через пару тунелей без единого провода между ними — доказывает,
что союзятся все дорожки, а не одна), `tunnel_is_direction_agnostic`,
`tunnels_with_different_labels_stay_unconnected`, `tunnels_with_empty_
label_stay_unconnected` (пустая метка — безобидна, как и в Java). 102
теста всего, 4 новых, 98 старых не тронуты.

### Ground/Power, Controlled Buffer, Decoder — следующая волна по частоте в реальном проекте

Продолжение того же разбора трёх `.circ` пользователя (CdM-8 + манкала).
Выбраны по месту в таблице частот после `Tunnel`: `Controlled Buffer` (32),
`Ground`/`Power` (20/5), `Decoder` (15).

**`Ground`/`Power`** (`std/wiring/Ground.java`/`Power.java`) — оказались не
отдельным видом узла вообще: `propagate()` у обоих — буквально `state.
setPort(0, Value.repeat(FALSE/TRUE, width), 1)`, то есть по форме идентично
`Constant.propagate`'s `setPort(0, Value.createKnown(width, value), 1)`.
Компилируются напрямую в уже существующий `TemplateNode::Constant` с
`value=0` (`Ground`) или `value=`все единицы (`Power`) — ни одного нового
варианта `Gate`/`TemplateNode`, ноль нового рантайм-кода, корректность по
построению (переиспользуется уже проверенный `Constant`).

**`Controlled Buffer`** (`std/gates/ControlledBuffer.java`, только
не-инвертирующий вариант `FACTORY_BUFFER` — "Controlled Inverter" ни разу
не встретился в реальных файлах, поэтому не реализован) — новый `Gate::
ControlledBuffer { bits }` в категории `logic` (тот же Java-пакет
`std.gates`). Важная деталь, расходящаяся с уже реализованными `Mux`/
`Demux`: там неподключённый (`Unknown`) enable по конвенции Logisim
считается "активным" (`enable_status`). У `ControlledBuffer` — наоборот,
`Unknown` сгруппирован с `Error` в самом `propagate()` (`else if (control
== Value.ERROR || control == Value.UNKNOWN)`) — недоопределённый control
даёт явный `Error` на выходе, а не пропуск данных. Только `control ==
Zero` даёт ожидаемое "отключено" (`Unknown`/высокий импеданс). Ветка с
`Value.NIL` (зависящая от глобальной опции проекта "как трактовать
неопределённый гейт", которую мы не моделируем) недостижима через обычное
чтение порта — сознательно схлопнута в случай `Zero`.

**`Decoder`** (`std/plexers/Decoder.java`) — в отличие от `ControlledBuffer`,
полностью повторяет конвенцию `Mux`/`Demux` (`Unknown` enable = активен),
поэтому переиспользует уже проверенные `decode_select`/`enable_status` из
`plexers.rs` без изменений. По сути это `Demux` без входа данных и с
выходами, зафиксированными на 1 бит (`BitWidth data = BitWidth.ONE`
хардкод в Java) — выбранный выход читает `One`, остальные — `tristate ?
Unknown : Zero`, при полном отключении — `disabled_zero`-зависимое
значение, теми же двумя независимыми флагами, что уже были у `Demux`.

Проверено юнит- и компиляционными тестами: 115 тестов всего (было 102),
13 новых, 102 старых не тронуты. Заодно поправлены все clippy-варнинги,
копившиеся с прошлых итераций (`if_same_then_else` в `Bit::combine`,
`should_implement_trait` на `Bit::not` — решено оставить инвариантным
методом с `#[allow]`, а не переводить на `impl Not`, поскольку это
потребовало бы `use std::ops::Not;` в каждом файле, где `.not()`
вызывается, ради нулевой выгоды; плюс мелкие `needless_lifetimes`/
`needless_range_loop`/`bool_assert_comparison` в `engine`).

### LED/Button/Bit Extender/Priority Encoder

Ещё одна волна того же разбора трёх `.circ` пользователя. По частоте:
`LED` — 15, `Button` — 13, `Bit Extender`/`Priority Encoder` — по 2.
**Не реализовано**: `Hex Digit Display` (42 вхождения — самый частый
компонент во всей "периферийной" группе, обогнал даже `Controlled
Buffer`'s 32) — раньше по ошибке посчитал его вместе с LED/Button
("70 вхождений") при выборе, что делать дальше; на деле это отдельный,
более сложный компонент (декодирует значение в 7-сегментный код), сюда
не попал и остаётся открытым пунктом.

**`LED`/`Button`** (`std/io/Led.java`/`Button.java`) — как и `Ground`/
`Power`, оказались не отдельными видами узлов вообще. `Led.propagate`
буквально сохраняет то, что пришло на единственный 1-битный вход (для
покраски/логгера) — ровно то же самое, что и так делает `OutputPin.eval`;
у `LED` при этом нет атрибута `width` в принципе, всегда 1 бит.
`Button.propagate` читает `state.setPort(0, val, 1)` из внутреннего
состояния "нажата/не нажата", которое `Poker.mousePressed/Released`
переключает в `TRUE`/`FALSE` — ровно то же самое, что уже делают `on`/
`off` у `InputPin { bits: 1 }` (которые уже существовали до этой сессии).
Компилируются напрямую в `TemplateNode::OutputPin{bits:1}`/`InputPin{
bits:1}` — снова ноль нового рантайм-кода.

**`Bit Extender`** (`std/wiring/BitExtender.java`) — новый `Gate::
BitExtender { in_bits, out_bits, mode }` в категории `wiring`. Логика
почти один в один совпадает с `Value.extendWidth`: если `out_bits <=
in_bits` — обрезка (берём младшие биты), иначе — досыпаем старшие биты
значением `mode` (`zero`/`one` — фиксированный бит; `sign` — повторяем
старший бит самого входа; `input` — повторяем значение отдельного
1-битного управляющего пина, который существует только в режиме
`input`). Важная деталь: заполняющий бит вычисляется **один раз**, а не
заново для каждой добавленной позиции — имеет значение, когда это не
константа, а сам бит может быть `Unknown`/`Error` (`sign`/`input`
режимы).

**`Priority Encoder`** (`std/plexers/PriorityEncoder.java`) — новый
`Gate::PriorityEncoder`. По интерфейсу похож на `Decoder` (n
однобитных входов + `enable_in`, `select_bits`-разрядный `out`), но
внутренняя логика **сознательно проще**, чем уже проверенные
`enable_status`/`decode_select` у `Mux`/`Demux`/`Decoder` — и это
реальное расхождение, не совпадение:
- `enabled = en != Value.FALSE` — простая проверка без отдельной ветки
  для `Error`, то есть `Error` на enable здесь считается "активным", а
  не конфликтом (в отличие от `Mux`/`Demux`/`Decoder`).
- каждая из n линий данных проверяется как `== Value.TRUE` — `Error`/
  `Unknown` на конкретной линии просто читается как "не установлена",
  никакого распространения ошибки на весь результат.
- побеждает **самый старший** установленный индекс (перебор с `n-1`
  вниз).
- выход `enable_out` — сигнал каскадирования: `One` только если сама
  секция включена, но ничего не нашла; `group_signal` — `One` ровно
  когда что-то нашлось.

Проверено юнит- и компиляционными тестами: 129 тестов всего (было 115),
14 новых, 115 старых не тронуты. Clippy чист.

### Совместимость с `.circ` (Logisim) — обязательное требование

Свой JSON-формат выше — не замена, а дополнение. `.circ` (XML-формат
оригинального Logisim) должен **импортироваться** полностью: пользователь
открывает существующий `.circ`-файл, мы конвертируем его во внутреннюю
JSON-схему, дальше всё работает как обычно. Обратный экспорт (JSON → `.circ`)
по умолчанию не требуется — не в скоупе, пока явно не понадобится.

Целевой диалект — **классический оригинальный Logisim**, не
Logisim-evolution: финальная опубликованная версия — **Logisim 2.7.1**
(21 марта 2011, cburch.com/logisim; разработка официально приостановлена
11 октября 2014, новых релизов с тех пор не было) — задаёт формат `.circ`
и набор компонентов, под который проектируется импортёр. Расширения Logisim-evolution (VHDL-компоненты, кастомные
appearance и т.п.) — вне скоупа; если такие файлы всё же встретятся на
импорте, поведение по умолчанию — понятная ошибка/предупреждение о
неподдерживаемом элементе, а не попытка угадать семантику или тихо
проигнорировать часть схемы.

Что это тянет за собой архитектурно:
- **Это не просто разбор XML, а воспроизведение семантики** компонентов
  Logisim — задержки распространения по умолчанию, поведение tri-state
  вентилей, вывод ширины шины у splitter'ов и т.д. Иначе схема визуально
  импортируется, но неверно симулируется. Из этого следует, что требование
  фактически задаёт **нижнюю границу охвата встроенной библиотеки компонентов
  движка** (§3/§10): она должна с самого начала покрывать библиотеку
  классического Logisim (wiring, gates, plexers, arithmetic, memory, I/O —
  штатный набор его палитры), а не "пару вентилей для старта" — это меняет
  оценку объёма фазы 2 дорожной карты.
- **XML от третьих лиц — та же осторожность, что в §12**: `.circ`-файлы
  часто присылают друг другу, парсер должен быть настроен без DTD/external
  entity resolution (защита от XXE), не доверять содержимому слепо.

Реализация — чистая функция `circXml -> внутренняя JSON-схема`, без
браузерных API, значит работает и в браузере, и в Node (для native CLI —
через Node-обёртку, если понадобится пакетная конвертация библиотеки схем в
CI/тестах). Порт на Rust для полностью Node-независимого native-пути —
по необходимости, не в v1 по умолчанию (см. §14).

### Оригинальный Logisim как reference-oracle (`logisim-port/`)

Решение: держим в репозитории отдельную директорию `logisim-port/` с
исходником **оригинального (классического) Logisim**, портированным на
Gradle — не как часть продукта, а как эталон для сверки. Не входит ни в
pnpm-, ни в Cargo-workspace продукта (§8) — самостоятельный vendored
инструмент.

Обоснование: у классического Logisim есть headless CLI-режим —

```
java -jar logisim.jar circuit.circ -tty table
```

(тикает часы, гоняет распространение сигналов, печатает таблицу в консоль,
без GUI — см. `docs/2.7/en/html/guide/verify` в исходниках/сайте проекта).
Это даёт настоящий **oracle** для golden-тестов (§7) и для проверки
семантики `.circ`-импортёра (§9): один и тот же `.circ` + вектор входов
прогоняется и через оригинальный Logisim, и через наш движок, результаты
сравниваются автоматически — надёжнее, чем вручную придуманные ожидаемые
значения. Так как совместимость решено делать именно с классическим
Logisim, а не evolution (§9), эталон согласован с этим выбором, а не
отдельная тема.

Порт на Gradle — небольшая задача, Swing/AWT исходник старый, но обратно
совместимый, должен собираться на современном JDK без серьёзной
переработки. Приоритет порта — получить собираемый jar с рабочим
`-tty`-режимом для автоматизации, а не довести GUI до идеала; сам
Swing-интерфейс полезен по минимуму — как дополнительная возможность
визуально сверяться при проектировании редактора, не как основная цель.

**Статус: исходник уже скачан.** Чекаут сделан из официального SVN-репозитория
на SourceForge (`svn://svn.code.sf.net/p/circuit/code`), тег `tags/2.7.1`
(revision 247, 2011-03-22, автор carlburch — соответствует релизу 2.7.1
точно, не более поздний trunk) — в `logisim-port/logisim-2.7.1/`. На
SourceForge в файлах релиза (`/files/2.7.x/2.7.1/`) лежат только бинарники
(jar/exe/dmg), исходник доступен только через SVN, поэтому потребовалась

  не мусор — оставлена как есть, без вопросов.

содержимое расползлось по нормальным местам:
- `logisim-2.7.1/src/com` → `src/main/java/com` (стандартный путь Gradle,
  кастомный `sourceSets` в build-скрипте больше не нужен вообще);
- `logisim-2.7.1/src/resources` → `src/main/resources/resources` —
  двойное `resources/resources` не опечатка: код грузит ресурсы по
  захардкоженным путям вида `getResourceAsStream("resources/logisim/...")`
  и `new LocaleManager("resources/logisim", ...)`, то есть буквальная
  папка `resources` должна остаться на classpath — раз исходник не трогаем,
  просто кладём его так, как он этого ожидает;
- `libs/`, `doc/`, `notes/`, `scripts/`, `xlate/` — стали обычными
  top-level папками рядом с `src/`, без изменений внутри.

Инструменты: `openjdk@17` (LTS, не «совсем старая», но и не последняя
25/26, которая уже ломает часть Swing-совместимости) + `gradle` из brew —
последний нужен был разово, чтобы сгенерировать Gradle wrapper
(`./gradlew`), дальше сборка идёт только через него, глобальный `gradle`
для проекта больше не требуется. `java.toolchain.languageVersion` в
`build.gradle` задаёт версию декларативно (17) — какой конкретно JDK её
предоставит, решает сам Gradle: локальный автодетект плюс плагин
`org.gradle.toolchains.foojay-resolver-convention` в `settings.gradle` на
случай, если подходящего JDK на машине нет (тогда он будет скачан сам).
Никакого захардкоженного пути к JDK в конфиге нет.

Что пришлось чинить, чтобы исходник 2011 года собрался под современный
тулчейн — и почему каждый раз выбран не «флаг в обход», а причина:
- **BOM в одном файле.** `com/cburch/draw/shapes/CurveUtil.java` начинался
  с байтов `EF BB BF` (UTF-8 BOM) — javac падал с `illegal character
  '﻿'`. Первая попытка — включить `options.encoding = 'UTF-8'` в
  `build.gradle` — по сути обход конкретно этого файла компилятором,
  а не исправление аномалии. По итогу выбран более прямой путь: байты BOM
  вырезаны из этого единственного файла (`tail -c +4`) — это чисто
  маркер кодировки, ни один видимый символ/строка кода не изменились,
  так что принцип "не трогаем содержимое вендоренного исходника" не
  нарушен, только убран невидимый лишний байт. Проверено, что это
  единственный файл с BOM во всём дереве.
- **`TreeNode.children()` — не байтовая, а сигнатурная несовместимость.**
  `SimulationTreeNode` и `ComponentSelector.OptionNode` переопределяют
  `javax.swing.tree.TreeNode.children()`, но в современном JDK у этого
  метода интерфейса generic-сигнатура (`Enumeration<? extends TreeNode>`),
  а исходник 2011 года переопределяет его как `Enumeration<?>` — это
  системная несовместимость (та же ошибка была бы на любом JDK 9+, не
  специфично для 17), не что-то, что можно списать на конкретный файл.
  Решено компилировать `--release 8` (`options.release.set(8)` на
  `JavaCompile`) — javac (сам всё ещё JDK 17) при этом типизирует код по
  API-срезу версии 8 (через встроенный `ct.sym`), где эта generic-сигнатура
  ещё не существовала. Это не то же самое, что "собирать на Java 8" — это
  ось "на чём собираем" (JDK 17, из toolchain) отдельно от оси "под какой
  API проверяем совместимость" (8, ровно под возраст этого кода) — и это
  штатный, предназначенный для таких случаев механизм javac, а не
  специальный обходной флаг под один симптом.

Итог: `./gradlew build` даёт один fat jar (`build/libs/logisim-2.7.1.jar`,
все `libs/*.jar` распакованы внутрь — так же, как делал оригинальный
`create-jar.py`). Проверено:

```
java -jar build/libs/logisim-2.7.1.jar doc/circs/verify.circ -tty table
```

— запускается без GUI, печатает табличный вывод и завершается с кодом 0
(конкретно у этого файла — `verify.circ`, судя по названию, возможно,
собственный тестовый фикстур авторов Logisim для проверки самого `-tty` —
вывод показывает состояние ошибки `E` на первом такте; это поведение
самой схемы/семантики симуляции, не сбой сборки; разбор конкретных
семантических деталей — уже задача этапа golden-тестов, не этого шага).
Главное для шага 1 подтверждено: **jar собирается современным тулчейном
и headless-режим работает** — сборка готова к использованию как oracle.

## 12. Безопасность

Разбираю по тем же двум слоям плагинов из §5, потому что у них принципиально
разный достижимый уровень доверия — общего решения "просто песочница" не
хватит на оба.

### Логические (WASM) плагины — сильная модель, потому что она дешёвая

Главный принцип: **минимизация импортов**. WASM-модуль по построению не
может ничего, чего ему явно не предоставили через imports — у него нет
амбиентных прав на файлы/сеть/DOM. Если ABI компонента — чистая функция
`eval(inputs, state) -> outputs, new_state` и хосту не нужно давать плагину
вообще никаких host-функций (или только безопасные: логирование,
детерминированный источник времени для симуляции), то песочница практически
герметична сама по себе, без доп. усилий:

- **Браузер**: хост (наш JS/TS bridge) сам решает, какой import-object
  давать при `WebAssembly.instantiate` — не давать доступ к DOM/`window`/
  сети. Компонентному плагину эти возможности и не нужны в принципе.
- **Native/CLI/Tauri**: инстанцировать плагины через `wasmtime` **без WASI**
  по умолчанию — тогда у модуля нет доступа к файловой системе/сети вообще.
  Если какому-то классу плагинов (например, плагин импорта/экспорта
  формата) реально нужен файловый доступ — WASI preview 2 с явным
  preopen конкретной директории (capability-based: доступ только к тому,
  что явно выдано, не ко всей ФС).
- **Лимиты ресурсов** — обязательны, т.к. память-safety ≠ защита от зависания
  или OOM: fuel/epoch-based прерывание в wasmtime (лимит на "шагов
  выполнения" за один вызов `eval`), верхняя граница на linear memory
  (`max_pages`). В браузере честного прерывания зависшего wasm-вызова из
  главного потока не бывает — поэтому недоверенные плагины стоит грузить в
  Worker (см. §3), откуда их можно `terminate()`, если `eval` не уложился в
  таймаут.
- **Детерминизм как побочный бонус**: тот же запрет на импорт "сырых"
  `Date.now()`/рандома, который снижает поверхность атаки, заодно защищает
  воспроизводимость симуляции (golden-тесты §7, повторяемые прогоны) —
  безопасность и корректность тут тянут в одну сторону, не конфликтуют.

### UI-плагины (JS/Vue) — слабая модель, надо явно это признать

Здесь всё наоборот: JS-плагин в контексте Vue-приложения по умолчанию имеет
полный доступ к DOM, `localStorage`, сети — то есть теоретически может
воровать данные открытого проекта или встраивать произвольный контент.
Полноценно изолировать это дорого (iframe с `postMessage`-протоколом, как у
VS Code webviews / Figma plugins) — для v1 закладываю **пониженную планку
доверия**, а не сэндбокс: грузим только явно установленные пользователем
UI-плагины, без автозагрузки из недоверенных источников, без "маркетплейса"
на старте. Изоляцию через iframe стоит держать в уме как путь роста, но не
делать блокером первой версии — иначе не сдвинемся с места ради риска,
которого пока нет (нет стороннего маркетплейса — нет стороннего кода).

### Файлы проектов, ссылающиеся на плагины

Если файл схемы (§9) может декларировать "для этого проекта нужен плагин X"
— нельзя тихо auto-load'ить и исполнять такой плагин при открытии файла,
полученного от кого-то другого. Нужен явный запрос подтверждения у
пользователя (по аналогии с "документ с макросами" в офисных пакетах),
особенно если плагин — из внешнего/незнакомого источника.

## 13. Установка плагинов без пересборки (drop-in файл в директорию)

Это возможно и нормально для native-таргетов, но именно **потому что мы
выбрали WASM**, а не потому что "любой плагин так можно". Стоит явно
проговорить, почему альтернатива была бы проблемой, и отдельно — что для
браузерной сборки "директория" не имеет прямого аналога.

### Почему WASM, а не нативная Rust-библиотека (dylib/`cdylib` + `dlopen`)

У Rust **нет стабильного ABI между версиями компилятора** — плагин,
собранный `rustc` другой версии, чем хост, при загрузке через `dlopen`
может не просто не заработать, а упасть с UB (несовпадение layout структур,
calling convention и т.п.). Это реальная и известная проблема нативных
Rust-плагинов "просто положи `.so`/`.dylib`/`.dll` в папку". WASM-модуль
таких проблем не создаёт: формат `.wasm` — сам по себе стабильный ABI,
интерпретируемый рантаймом (`wasmtime`), а не сырой машинный код с
compiler-specific layout. То есть решение "плагины через WASM" из §5 —
это не только про песочницу и переносимость в браузер, но и то, что вообще
делает "drop-in файл без пересборки хоста" безопасным и надёжным на native.
Если бы был выбран native dylib-подход, "просто добавить файл" был бы
хрупким и рискованным по умолчанию, а не просто "требует доп. работы".

### Native / CLI / Desktop (Tauri) — прямой fit

- Директория плагинов: `plugins/` рядом с исполняемым файлом или в
  стандартной пользовательской конфиг-директории (`~/.config/revlog/plugins`
  и аналоги на других ОС).
- Хост на старте (или по watch на директорию — для hot-reload в дев-режиме)
  сканирует `*.wasm`, инстанцирует через `wasmtime` с ограничениями из §12,
  без пересборки самого приложения — это штатный сценарий, не требует
  ничего специального сверх того, что уже спроектировано в §5/§6.

### Browser / Web — другая модель, нет "директории" как таковой

У браузера нет амбиентного доступа к произвольной директории на диске, так
что буквальный аналог "положил файл — плагин появился" не переносится
напрямую. Нужно отдельно спроектировать один из вариантов (или оба):

1. **Явный выбор файла пользователем** — `<input type=file>` /
   File System Access API (`showOpenFilePicker`), с явным consent-диалогом
   браузера. Чтобы плагин не терялся между сессиями — сохранять байты
   `.wasm` в IndexedDB и переинстанцировать при следующей загрузке
   (по-прежнему без сети/маркетплейса).
2. **Плагин по URL / хостед-реестр** — ближе к модели расширений браузера
   или marketplace; добавляет отдельный класс рисков (доверие к реестру,
   supply chain, нужны хеши/подписи) — это уже не то же самое, что "плагины
   на диске", и стоит явно решить, нужен ли такой реестр вообще для v1,
   или ограничиться (1).

Т.е. "установка без пересборки" — решённая проблема для desktop/CLI прямо
сейчас архитектурой из §5, но для web-сборки это отдельный нерешённый
UX/security вопрос, который стоит закрыть до реализации плагинного слоя
(фаза 5 в §10), а не постфактум.

### Манифест и версионирование ABI

Раз плагины собираются независимо и в разное время, хосту нужно понимать
совместимость **до** попытки вызвать неизвестный код:

- Плагин — самодостаточный `.wasm`-файл с метаданными **внутри** (custom
  section: id, semver плагина, версия `plugin-abi`, декларация нужных
  возможностей типа "нет"/"нужен файловый доступ", схема конфигурации для
  авто-генерации property-панели). Встраивать метаданные в сам wasm-модуль,
  а не в отдельный JSON рядом с ним по имени — меньше шансов, что
  пользователь при ручном drop-in занесёт файлы врозь или перепутает пару.
- `plugin-abi` (крейт из §8) версионируется по semver; хост при загрузке
  сверяет заявленную версию ABI и **отказывает с понятной ошибкой** при
  несовместимости мажорной версии, а не падает непредсказуемо. Это то же
  соображение, что и с Rust ABI выше, только на уровне нашего собственного
  контракта, а не компилятора.

- **JS-логика в плагинах** (§5) — сознательно закрыл вопрос в пользу
  WASM-only для логики; если это неприемлемо (например, хочется учебных
  JS-скриптовых компонентов без компиляции) — это меняет архитектуру
  headless-запуска, стоит явно подтвердить или отвергнуть.
- **SharedArrayBuffer / COOP-COEP** (§3) — zero-copy обмен состоянием
  требует специфических HTTP-заголовков от хостинга; если деплой (например,
  GitHub Pages без контроля заголовков) это не позволяет — придётся
  оставаться на copy-based обмене через `postMessage`, что нормально, но
  чуть медленнее.
- **WebView-расхождения Tauri** (§6) — стоит рано прогнать canvas-рендер на
  WebView2/WebKit/GTK-WebKit, чтобы не упереться в баг рендеринга поздно.
- **Выбор native WASM-рантайма** (§12/§13) — `wasmtime` выглядит более
  очевидным выбором, чем `wasmer` (активнее развивается направление
  безопасности/метеринга, лучше документирован WASI preview 2) — но стоит
  подтвердить перед тем, как на нём завязывается плагинный слой.
- **Web-модель установки плагинов** (§13) — файловый пикер + IndexedDB
  против хостед-реестра, нужно решение до фазы 5.
- **UI-плагины и iframe-изоляция** (§12) — сознательно не делаю блокером v1,
  но если ожидается сторонний маркетплейс UI-плагинов раньше, чем кажется
  сейчас, изоляцию стоит планировать заранее, а не пристраивать задним
  числом.
- **Нужен ли экспорт обратно в `.circ`** (§9) — по умолчанию план считает,
  что не нужен (только импорт); если всё же нужен — это отдельная, не
  тривиальная симметричная задача (наш формат может выражать вещи, которых
  нет в `.circ`), стоит подтвердить сейчас, а не после того как всё
  спроектировано только "в одну сторону".
- ~~`simulate <n>` при нескольких независимых часах в схеме~~ — **закрыто**,
  см. "`Clock`/`Register` — один общий счётчик тактов" выше: независимых
  часов в Logisim не бывает, есть один общий счётчик и per-instance
  делители периода, так что `n` однозначно значит "n тактов общего
  счётчика".
- **XOR/XNOR-режим `XOR_ODD`** (см. "Библиотека вентилей" выше) — Logisim
  поддерживает два режима поведения при arity > 2 ("ровно один вход
  истинен" — наш дефолт, и цепочка `xor` — не смоделирована); для 2-входовых
  вентилей разницы нет, так что не блокер, но всплывёт при импорте `.circ`
  схемы, которая явно выставила `xor: "odd"`.
- **`PullResistor` на широкой шине** (см. "Библиотека вентилей" выше) — у
  нас он однобитный; у настоящего Logisim ширина выводится из сети, к
  которой он подключён (`BitWidth.UNKNOWN`). Нужен вывод ширины по сети в
  `compile.rs`, которого пока нет — не блокер (можно ставить по резистору на
  бит), но стоит решить до `.circ`-импорта, где такие резисторы уже
  встречаются готовыми, без явного атрибута ширины.
- **`Splitter`'s `order = -1`** (см. "Splitter — не компонент" выше) —
  `SplitterAttributes.computeDistribution` поддерживает и убывающее
  распределение (используется только Logisim-евской командой меню
  "distribute" в другую сторону, не отдельным атрибутом на схеме); наша
  схема моделирует только `order = 1` плюс явный `"bits"`-оверрайд, которым
  можно выразить любое конкретное распределение вручную — не блокер, но
  `.circ`-импортёру, если он захочет автоматически угадывать "который из
  двух дефолтов" был использован в исходном файле, эта деталь понадобится.
- **`Multiplier`'s точная эвристика для частично неопределённых операндов**
  (см. "Multiplier/Divider — найдены реальные баги" выше) — у настоящего
  `Multiplier.computeProduct` низкие биты результата могут быть точно
  известны, даже если часть операнда ещё не устоялась (`getKnown`'s
  префиксный подсчёт); наша реализация огрубляет это до "любой `Unknown`
  где угодно → весь результат `Unknown`". Не блокер (тот же класс упрощения,
  что уже принят для `XOR_ODD`) — сказывается только в те несколько тактов,
  пока сигналы ещё оседают, финальное (settled) значение не отличается.
