# revlog — план переписывания Logisim на современный стек

Статус: черновик архитектуры, git ещё не подключён. Документ фиксирует принятые
решения и объяснения к ним, чтобы не передумывать каждый раз заново.

## 0. Цель и рамки

Logisim (Java) — редактор схем + событийный симулятор цифровой логики
(вентили, шины, подсхемы как компоненты, память, таймдиаграммы). Переписываем
с нуля на современный стек, сохраняя суть: редактор схем + симулятор + плагины
+ headless-режим + возможность собрать десктоп-приложение.

Важно: оригинальный Logisim (и Logisim-evolution) под GPL. Переписывание —
clean-room: проектируем архитектуру и модель данных заново, не копируя код
и не портируя классы 1:1. Формат файлов тоже будет свой (см. §4), не .circ/XML.

## 1. Общая архитектура (слои)

```
┌────────────────────────────────────────────┐
│ UI Shell — Vue 3 + TypeScript               │  меню, палитра компонентов,
│                                              │  инспектор свойств, файлы,
│                                              │  настройки, диалоги
├──────────────────────────────────────────────┤
│ Editor Core — чистый TS/JS (без Vue)        │  сцена схемы, canvas-рендер,
│                                              │  hit-testing, drag/wiring,
│                                              │  undo/redo, сериализация
├──────────────────────────────────────────────┤
│ Engine Bridge — тонкий TS-слой               │  компиляция схемы → netlist IR,
│                                              │  батчинг вызовов в WASM,
│                                              │  чтение состояния пинов
├──────────────────────────────────────────────┤
│ Simulation Engine — Rust                     │  событийный планировщик,
│  → wasm32 (браузер)                          │  компонентная модель,
│  → native (CLI/тесты/Tauri)                  │  плагины через общий ABI
└────────────────────────────────────────────┘
```

Ключевая идея, которая объясняет пункты 2–4 разом: **движок ничего не знает
про UI**, а Editor Core ничего не знает про WASM-детали — он говорит с
движком через Engine Bridge, у которого есть заглушка (mock) для тестов
редактора без запуска симулятора. Это разделение — то, что делает headless-
режим (п.4) не отдельной фичей, а естественным следствием архитектуры, а не
доп. работой.

## 2. UI: Vue + TypeScript (shell) / чистый TS (редактор схем)

Решение подтверждаю — это правильное разделение, аналог того, как устроены
Excalidraw/tldraw/Figma: canvas-редактор с интенсивным взаимодействием
(перетаскивание, рисование проводов, hit-testing на каждый mousemove) плохо
уживается с реактивностью Vue — лишние ре-рендеры и накладные расходы на
отслеживание зависимостей там, где нужен прямой императивный контроль над
кадром. Vue хорош для "обычного" UI: панели, диалоги, инспектор свойств,
которые меняются редко и по явным событиям.

- Editor Core — chërный TS, свой scene graph, свой render loop на Canvas2D
  (не SVG — деградирует на схемах с тысячами элементов; не WebGL — оверкилл
  для 2D-схемотехники, усложнение без реальной необходимости).
- Пространственный индекс (grid/quadtree) для hit-testing и viewport culling
  на больших схемах — иначе даже быстрый движок симуляции упрётся в тормоза
  рендера.
- Editor Core экспортирует явный API (события: componentAdded, wireDrawn,
  selectionChanged...) — Vue-shell подписывается на него, а не наоборот.
  Editor Core не импортирует Vue вообще, что позволяет переиспользовать его
  без Vue (например, в тестах, или если позже понадобится другой UI-фреймворк).

## 3. Движок: Rust → WASM

Максимальная производительность и headless — по сути одно и то же решение,
не два отдельных. Обоснование Rust: cache-friendly data-oriented дизайн
(structure-of-arrays, компоненты и пины — целочисленные индексы, а не
объекты со ссылками), предсказуемая производительность без GC-пауз, и
единая кодовая база, которая компилируется в разные таргеты без переписывания
логики:

- `wasm32-unknown-unknown` + wasm-bindgen — для браузера.
- нативный таргет (rlib/binary) — для CLI, `cargo test`, встраивания в Tauri
  напрямую (десктоп-сборка вообще может не проходить через WASM — движок
  как обычный Rust-крейт, ещё быстрее).

### Модель симуляции
Сохраняем событийную (discrete-event) модель, как в оригинале, а не
"решать до стабилизации топологически" — она нужна, чтобы корректно
обрабатывать задержки распространения сигнала, генераторы/защёлки с обратной
связью и обнаружение осцилляций. Планировщик — очередь событий по времени
(min-heap), компоненты — плоские массивы, "грязные" компоненты — очередь
индексов на пересчёт. Это прямое попадание в сильные стороны Rust
(cache locality, отсутствие указательной "паутины").

### Встроенные компоненты vs плагины
Базовые вентили/мультиплексоры/регистры/ALU/RAM — реализованы нативно прямо
в движке (не через WASM-в-WASM), чтобы не платить накладные расходы на самом
горячем пути. Плагин-компоненты — отдельные WASM-модули с тем же интерфейсом
(см. §5), но чуть медленнее из-за границы вызова — это нормально, это не
hot path большинства схем.

### Граница TS ↔ WASM
Гибридный подход: wasm-bindgen для "холодных" операций (загрузка схемы,
регистрация плагина, редкие вызовы) — там важна эргономика, не скорость.
Для горячего пути (шаг симуляции, чтение состояния пинов) — свой протокол
поверх линейной памяти: движок пишет состояние в preallocated буфер,
JS читает его как `Uint8Array`/`DataView` без сериализации через
wasm-bindgen на каждый вызов. Один "тик" симуляции = один вызов в WASM,
а не вызов на каждое событие — иначе граница вызова съест весь выигрыш
от Rust.

### Воркер и потоки
Долгий/непрерывный запуск (свободно бегущие часы) стоит гонять в отдельном
Web Worker, чтобы не блокировать UI-поток редактора. Обмен состоянием —
через transferable ArrayBuffer каждый кадр, либо SharedArrayBuffer для
zero-copy — но это требует заголовков COOP/COEP на сервере, так что это
улучшение фазы 2+, не день 1 (флагирую как риск/зависимость от деплоя).

## 4. Headless-режим (запуск без UI)

Не отдельная фича, а следствие §3: раз движок — чистый Rust-крейт без
знания о DOM, он одинаково доступен как:

- нативный CLI-бинарь (`engine-cli`) — прогнать схему с вектором входов,
  получить трассу выходов, без браузера вообще;
- WASM-модуль из Node.js — тот же движок, что в браузере, без UI;
- библиотека, встраиваемая в другой Rust-код (например, в тестовый раннер
  или в будущем бэкенд).

Это же прямо закрывает часть п.7 (тестирование) — самый быстрый цикл
обратной связи это `cargo test` без браузера и без WASM-прослойки вообще.

## 5. Система плагинов: WASM-only логика, JS — только для UI-надстроек

Разделяю плагины на два принципиально разных слоя вместо единого решения
"или JS, или WASM" — потому что у логических (симуляционных) плагинов и
у UI-плагинов разные требования:

**Логика (поведение компонентов) — только WASM.**
Причина: движок должен одинаково работать в браузере, в native CLI и в
тестах (§4). Если разрешить компонентам-плагинам логику на JS, headless/
native запуск либо теряет эти компоненты, либо требует тащить в native-
бинарь встроенный JS-движок (толсто, медленно, лишняя поверхность атаки).
WASM-плагин пишется на чём угодно (Rust, C, AssemblyScript, TinyGo) — язык
не важен, важен общий ABI (`init`, `eval(inputs) -> outputs`,
`pin_count`, `serialize_state`) — тот же контракт, что и у встроенных
компонентов внутри движка, то есть мы не изобретаем второй интерфейс.
Загрузку плагинного WASM-модуля делает хост (в браузере — JS через
`WebAssembly.instantiate`, в native — `wasmtime`/`wasmer` в CLI/Tauri), а не
сам движок изнутри себя — WASM-модуль не может сам инстанцировать другой
WASM-модуль без посредника-хоста, это техническое ограничение, которое надо
учитывать в реализации, а не только в теории.
Сэндбоксинг — бонус, а не только приём производительности: WASM
изолирован по памяти по построению, что важно, если плагины сторонние.

**UI/тулинг (кастомные property-панели, импорт/экспорт форматов, пункты
меню, темы) — JS/TS, опционально Vue-компоненты.**
Причина обратная: этому слою не нужно работать headless, зато нужна
хорошая DX (без шага компиляции, мгновенная перезагрузка, прямой доступ к
DOM/Vue). Риск встроенного JS-плагина, ломающего UI-поток — приемлем, т.к.
UI и так однопоточный/браузерный контекст; при необходимости позже можно
изолировать через Worker/iframe (по модели VS Code extension host), но это
не блокер для первой версии.

Итог: два ABI, а не один компромиссный — логика везде одинаково быстрая
и портируемая, UI-расширения максимально удобны для авторов. Это тот пункт
плана, который стоит явно обсудить перед реализацией — если вы хотите
разрешить JS и для логики компонентов (например, для простых учебных
компонентов), это возможно, но тогда придётся решать вопрос native/headless
отдельно (встраивать QuickJS-в-WASM для CLI — дорого и по сложности, и по
рантайму).

## 6. Упаковка: Tauri вместо Electron/NW.js (рекомендация)

Раз движок уже на Rust, Tauri — не просто "аналог Electron на Rust", а
прямая синергия: десктоп-бэкенд Tauri может линковать движок как обычный
Rust-крейт напрямую, вообще без WASM-границы — то есть десктопная сборка
потенциально быстрее веб-сборки, и это без дублирования кода (тот же крейт,
просто другой feature-флаг таргета).

Дополнительно: заметно меньший размер бинарника (единицы МБ против
100+ МБ у Electron, т.к. Tauri использует системный WebView, а не тащит
Chromium), меньше потребление памяти. Минус — системный WebView
(WebView2/WebKit/GTK-WebKit) даёт чуть больше расхождений в рендере между
платформами, чем гарантированно одинаковый Chromium в Electron; это
компромисс, на который стоит пойти, но явно закладываю как риск ниже.

NW.js не рекомендую рассматривать отдельно от Electron — те же минусы
(бандл Chromium+Node), но менее развитая экосистема и поддержка; если
Tauri по какой-то причине не подойдёт (нужны specific Node-only API,
экосистема электрон-плагинов), fallback — Electron, а не NW.js.

## 7. Тестирование

Базовая, но многослойная система, использующая headless-движок как основу:

- **Rust/engine**: `cargo test` — юнит-тесты компонентов, интеграционные
  тесты полных схем; `proptest` для проверки арифметических компонентов
  (сумматор, ALU) на случайных входах; golden-тесты — схема + вектор входов
  + ожидаемая трасса выходов, гоняются через native CLI в CI без браузера
  вообще (самый дешёвый и быстрый уровень тестирования).
- **WASM-граница**: `wasm-bindgen-test` — по минимуму, т.к. сам bridge-слой
  должен быть тонким (вся логика — в чистом Rust-крейте, который уже
  покрыт тестами выше).
- **TS/редактор**: Vitest для чистой TS-логики Editor Core (геометрия,
  hit-testing, undo/redo, сериализация схемы) — без браузера, быстро.
- **Vue-shell**: Vue Test Utils / Testing Library — точечно, для панелей.
- **e2e**: Playwright — нарисовать схему, запустить симуляцию в браузере,
  проверить результат/визуальный снапшот.
- **Импортёр `.circ`**: отдельный пласт golden-тестов на реальных
  `.circ`-файлах (из оригинального Logisim/Logisim-evolution, не только
  синтетических) — сверяем и результат импорта (структура схемы), и
  поведение при симуляции после импорта. Реальные файлы полезнее
  синтетических здесь, т.к. ловят расхождения семантики, которые вручную
  придумать сложно.
- CI: после появления git — прогонять `cargo test` + wasm build +
  `vitest` + Playwright на каждый push. Пока репозитория нет, это пункт
  "день 1 после git init", не блокер плана.

## 9. Формат файлов и модель данных

- Формат — версионированный JSON (`schemaVersion`), не XML/.circ: проще
  парсить и в TS, и в Rust, читаемее для будущих плагинов/скриптов.
- Источник истины — **визуальная схема** (позиции компонентов, точки
  проводов, конфигурация) — то, что сохраняется на диск. **Netlist IR**
  (плоский граф для движка) — производный, эфемерный артефакт компиляции,
  никогда не сохраняется, как байткод относительно исходника. Это разделение
  важно держать явным, иначе легко скатиться в сохранение "скомпилированного"
  состояния и потерять возможность просто отредактировать схему текстом.
- Подсхемы (иерархический дизайн) — компонент типа "instance of circuit N",
  как в оригинале; резолвится в netlist на этапе компиляции.

### Черновая JSON-схема (конверт) — Фаза 1

Реализовано: `crates/engine/src/file_format.rs` (source of truth, с serde) +
зеркальный `packages/editor-core/src/file-format.ts` (синхронизируется
руками, пока расхождение не станет болезненным — тогда стоит вернуться и
рассмотреть кодоген из одного источника).

Сознательно описан только **конверт** — структура файла (circuit → components
+ wires + annotations), а не то, какие типы компонентов существуют и какие у
них атрибуты. `type` и `attrs` на этом уровне непрозрачны (`type: String`,
`attrs: BTreeMap<String, JsonValue>`). Это не недосмотр: если сейчас
перечислить конкретные типы (AND/OR/Mux/Register/...) прямо в файловой схеме,
схема незаметно срастётся с API стандартной библиотеки компонентов — а её мы
спроектируем в Фазе 2, когда будет ясно, как выглядит `Component`-трейт в
движке. Схему файла придётся тогда либо переделывать, либо она будет тянуть
за собой промежуточные, поспешные решения. Библиотека компонентов — забота
каждой их реализации (какие атрибуты у AND-гейта решает код AND-гейта), не
общего конверта.

Что зафиксировано на уровне конверта (осознанные решения, не производные от
библиотеки компонентов):
- **Адресация типов** — `"core:AndGate"` / `"core:circuit/<name>"` (подсхема)
  / `"plugin:<plugin-id>/<component-id>"`. Это схема адресации (namespacing),
  а не перечень существующих типов — годится уже сейчас, не блокирует
  библиотеку компонентов и сразу задаёт единый способ ссылаться и на
  встроенные, и на плагинные компоненты (см. §5/§13).
- **Ориентация — `facing` (east/west/north/south), не угол поворота** —
  повторяет модель самого Logisim; нужно для точного воспроизведения
  семантики при импорте `.circ` (см. ниже), а не общая абстракция "на
  будущее".
- **Провода — двухточечные сегменты** (`from`/`to`), как в `.circ`; узлы
  (junctions) неявные, по совпадающим концам. Тоже прямое следствие
  требования совместимости с импортом, не произвольный выбор.
- **Аннотации (текстовые метки) — отдельная сущность**, не `components`: у
  них нет пинов, они никогда не попадают в netlist.
- id — строки, не числа: стабильнее при правках, читаемее в git diff,
  совпадает с адресацией компонентов/плагинов.

Не входит в этот черновик (сознательно отложено): конкретные значения
`core:*` (Фаза 2), контракт манифеста плагина внутри `attrs`/скоупа проекта
(§5/§13 уже описывают модель на уровне ABI, но не то, как именно плагинная
зависимость фиксируется в файле — уточнится вместе с ABI), экспорт JSON →
`.circ` (не в скоупе, см. ниже), формальная валидация (JSON Schema/ajv) —
пока двух синхронизированных наборов типов (Rust/TS) достаточно, добавлять
третий артефакт истины преждевременно.

### Совместимость с `.circ` (Logisim) — обязательное требование

Свой JSON-формат выше — не замена, а дополнение. `.circ` (XML-формат
оригинального Logisim) должен **импортироваться** полностью: пользователь
открывает существующий `.circ`-файл, мы конвертируем его во внутреннюю
JSON-схему, дальше всё работает как обычно. Обратный экспорт (JSON → `.circ`)
по умолчанию не требуется — не в скоупе, пока явно не понадобится.

Целевой диалект — **классический оригинальный Logisim**, не
Logisim-evolution: финальная опубликованная версия — **Logisim 2.7.1**
(21 марта 2011, cburch.com/logisim; разработка официально приостановлена
11 октября 2014, новых релизов с тех пор не было) — задаёт формат `.circ`
и набор компонентов, под который проектируется импортёр. Расширения Logisim-evolution (VHDL-компоненты, кастомные
appearance и т.п.) — вне скоупа; если такие файлы всё же встретятся на
импорте, поведение по умолчанию — понятная ошибка/предупреждение о
неподдерживаемом элементе, а не попытка угадать семантику или тихо
проигнорировать часть схемы.

Что это тянет за собой архитектурно:
- **Это не просто разбор XML, а воспроизведение семантики** компонентов
  Logisim — задержки распространения по умолчанию, поведение tri-state
  вентилей, вывод ширины шины у splitter'ов и т.д. Иначе схема визуально
  импортируется, но неверно симулируется. Из этого следует, что требование
  фактически задаёт **нижнюю границу охвата встроенной библиотеки компонентов
  движка** (§3/§10): она должна с самого начала покрывать библиотеку
  классического Logisim (wiring, gates, plexers, arithmetic, memory, I/O —
  штатный набор его палитры), а не "пару вентилей для старта" — это меняет
  оценку объёма фазы 2 дорожной карты.
- **XML от третьих лиц — та же осторожность, что в §12**: `.circ`-файлы
  часто присылают друг другу, парсер должен быть настроен без DTD/external
  entity resolution (защита от XXE), не доверять содержимому слепо.

Реализация — чистая функция `circXml -> внутренняя JSON-схема`, без
браузерных API, значит работает и в браузере, и в Node (для native CLI —
через Node-обёртку, если понадобится пакетная конвертация библиотеки схем в
CI/тестах). Порт на Rust для полностью Node-независимого native-пути —
по необходимости, не в v1 по умолчанию (см. §14).

### Оригинальный Logisim как reference-oracle (`logisim-port/`)

Решение: держим в репозитории отдельную директорию `logisim-port/` с
исходником **оригинального (классического) Logisim**, портированным на
Gradle — не как часть продукта, а как эталон для сверки. Не входит ни в
pnpm-, ни в Cargo-workspace продукта (§8) — самостоятельный vendored
инструмент.

Обоснование: у классического Logisim есть headless CLI-режим —

```
java -jar logisim.jar circuit.circ -tty table
```

(тикает часы, гоняет распространение сигналов, печатает таблицу в консоль,
без GUI — см. `docs/2.7/en/html/guide/verify` в исходниках/сайте проекта).
Это даёт настоящий **oracle** для golden-тестов (§7) и для проверки
семантики `.circ`-импортёра (§9): один и тот же `.circ` + вектор входов
прогоняется и через оригинальный Logisim, и через наш движок, результаты
сравниваются автоматически — надёжнее, чем вручную придуманные ожидаемые
значения. Так как совместимость решено делать именно с классическим
Logisim, а не evolution (§9), эталон согласован с этим выбором, а не
отдельная тема.

Порт на Gradle — небольшая задача, Swing/AWT исходник старый, но обратно
совместимый, должен собираться на современном JDK без серьёзной
переработки. Приоритет порта — получить собираемый jar с рабочим
`-tty`-режимом для автоматизации, а не довести GUI до идеала; сам
Swing-интерфейс полезен по минимуму — как дополнительная возможность
визуально сверяться при проектировании редактора, не как основная цель.

**Статус: исходник уже скачан.** Чекаут сделан из официального SVN-репозитория
на SourceForge (`svn://svn.code.sf.net/p/circuit/code`), тег `tags/2.7.1`
(revision 247, 2011-03-22, автор carlburch — соответствует релизу 2.7.1
точно, не более поздний trunk) — в `logisim-port/logisim-2.7.1/`. На
SourceForge в файлах релиза (`/files/2.7.x/2.7.1/`) лежат только бинарники
(jar/exe/dmg), исходник доступен только через SVN, поэтому потребовалась
установка `svn` (через `brew install svn` — единственный сторонний
инструмент, понадобившийся для этого шага).

Что выяснилось из самого исходника (важно для порта на Gradle):
- **Лицензия — GPLv2 или новее** (см. заголовки файлов, например
  `src/com/cburch/logisim/Main.java`). Значит: вендорить и коммитить этот
  исходник в наш репозиторий можно, сохраняя GPL-уведомления в этой
  поддиректории — но переносить/портировать сам код в наш новый Rust/TS
  движок нельзя, это заGPL'ило бы продукт. План и так предполагал
  clean-room переписывание без копирования кода (§0) — этот факт
  подтверждает решение, а не меняет его. Открытый вопрос про лицензию из
  §14 закрыт.
- **Сборка была не Ant, а самописные Python-скрипты**
  (`scripts/create-jar.py`, `copy_doc.py`, `doc2www.py` и т.д.) — top-level
  `build.xml` в дереве нет вообще. Порт на Gradle придётся писать с нуля по
  структуре `src/`, а не переносить существующий build-файл.
- **В `libs/` — 4 вендоренных сторонних jar'а**: `jh.jar` (JavaHelp, для
  системы помощи — есть на Maven Central как `javax.help:javahelp`),
  `colorpicker.jar`, `fontchooser.jar`, `MRJAdapter.jar`. Уточнение по
  `MRJAdapter`: изначально казалось мёртвым кодом под classic Mac OS, но
  в `MacOsAdapter.java` видно, что это не так — прямые вызовы
  `com.apple.eawt.*` там закомментированы построчно (маркер `//MAC`,
  переключался их собственной сборкой под конкретную ОС), а живой,
  кросс-платформенный путь идёт именно через `net.roydesign.mac.MRJAdapter`
  из этого jar'а. То есть библиотека активно используется в generic-сборке,
  не мусор — оставлена как есть, без вопросов.

**Чистка дерева (сделано).** Из `logisim-2.7.1/` убрано то, что точно не
нужно для сборки/использования как oracle: `www/` целиком (исходник
сайта проекта), из `doc/` — переводы `de/el/es/pt` (оставлены `en`, `ru`,
`circs`, `support`), из `xlate/` — `de/el/pt` и `guide/` (инструкция для
переводчиков-контрибьюторов, оставлен только `ru`). Проверено заранее:
код (`MenuHelp.java`) ссылается лишь на скомпилированный `doc/doc_en.hs`,
прямых зависимостей от убранных языковых каталогов в исходниках нет —
максимум Help-меню на других языках останется пустым, что не критично.
Также удалена `.svn/` (22MB из 42MB, наибольшая часть веса — метаданные
чужого VCS плюс pristine-копии уже удалённых файлов) — рабочая копия SVN
нам не нужна, это разовый чекаут для референса; при необходимости
воссоздаётся тем же `svn checkout` (см. выше). Итог: 42MB → **17MB**.
Не тронуты: `libs/` (сторонние jar'ы), `notes/` (release notes по
версиям), `scripts/` (оригинальные Python-скрипты сборки — полезны как
референс при портировании на Gradle), `src/` (сам исходник).

**Gradle-порт (сделано, шаг 1) — jar собирается, `-tty` работает.**

Структура переложена в стандартный Gradle-layout прямо на уровне
`logisim-port/` — промежуточная папка `logisim-2.7.1/` убрана целиком, её
содержимое расползлось по нормальным местам:
- `logisim-2.7.1/src/com` → `src/main/java/com` (стандартный путь Gradle,
  кастомный `sourceSets` в build-скрипте больше не нужен вообще);
- `logisim-2.7.1/src/resources` → `src/main/resources/resources` —
  двойное `resources/resources` не опечатка: код грузит ресурсы по
  захардкоженным путям вида `getResourceAsStream("resources/logisim/...")`
  и `new LocaleManager("resources/logisim", ...)`, то есть буквальная
  папка `resources` должна остаться на classpath — раз исходник не трогаем,
  просто кладём его так, как он этого ожидает;
- `libs/`, `doc/`, `notes/`, `scripts/`, `xlate/` — стали обычными
  top-level папками рядом с `src/`, без изменений внутри.

Инструменты: `openjdk@17` (LTS, не «совсем старая», но и не последняя
25/26, которая уже ломает часть Swing-совместимости) + `gradle` из brew —
последний нужен был разово, чтобы сгенерировать Gradle wrapper
(`./gradlew`), дальше сборка идёт только через него, глобальный `gradle`
для проекта больше не требуется. `java.toolchain.languageVersion` в
`build.gradle` задаёт версию декларативно (17) — какой конкретно JDK её
предоставит, решает сам Gradle: локальный автодетект плюс плагин
`org.gradle.toolchains.foojay-resolver-convention` в `settings.gradle` на
случай, если подходящего JDK на машине нет (тогда он будет скачан сам).
Никакого захардкоженного пути к JDK в конфиге нет.

Что пришлось чинить, чтобы исходник 2011 года собрался под современный
тулчейн — и почему каждый раз выбран не «флаг в обход», а причина:
- **BOM в одном файле.** `com/cburch/draw/shapes/CurveUtil.java` начинался
  с байтов `EF BB BF` (UTF-8 BOM) — javac падал с `illegal character
  '﻿'`. Первая попытка — включить `options.encoding = 'UTF-8'` в
  `build.gradle` — по сути обход конкретно этого файла компилятором,
  а не исправление аномалии. По итогу выбран более прямой путь: байты BOM
  вырезаны из этого единственного файла (`tail -c +4`) — это чисто
  маркер кодировки, ни один видимый символ/строка кода не изменились,
  так что принцип "не трогаем содержимое вендоренного исходника" не
  нарушен, только убран невидимый лишний байт. Проверено, что это
  единственный файл с BOM во всём дереве.
- **`TreeNode.children()` — не байтовая, а сигнатурная несовместимость.**
  `SimulationTreeNode` и `ComponentSelector.OptionNode` переопределяют
  `javax.swing.tree.TreeNode.children()`, но в современном JDK у этого
  метода интерфейса generic-сигнатура (`Enumeration<? extends TreeNode>`),
  а исходник 2011 года переопределяет его как `Enumeration<?>` — это
  системная несовместимость (та же ошибка была бы на любом JDK 9+, не
  специфично для 17), не что-то, что можно списать на конкретный файл.
  Решено компилировать `--release 8` (`options.release.set(8)` на
  `JavaCompile`) — javac (сам всё ещё JDK 17) при этом типизирует код по
  API-срезу версии 8 (через встроенный `ct.sym`), где эта generic-сигнатура
  ещё не существовала. Это не то же самое, что "собирать на Java 8" — это
  ось "на чём собираем" (JDK 17, из toolchain) отдельно от оси "под какой
  API проверяем совместимость" (8, ровно под возраст этого кода) — и это
  штатный, предназначенный для таких случаев механизм javac, а не
  специальный обходной флаг под один симптом.

Итог: `./gradlew build` даёт один fat jar (`build/libs/logisim-2.7.1.jar`,
все `libs/*.jar` распакованы внутрь — так же, как делал оригинальный
`create-jar.py`). Проверено:

```
java -jar build/libs/logisim-2.7.1.jar doc/circs/verify.circ -tty table
```

— запускается без GUI, печатает табличный вывод и завершается с кодом 0
(конкретно у этого файла — `verify.circ`, судя по названию, возможно,
собственный тестовый фикстур авторов Logisim для проверки самого `-tty` —
вывод показывает состояние ошибки `E` на первом такте; это поведение
самой схемы/семантики симуляции, не сбой сборки; разбор конкретных
семантических деталей — уже задача этапа golden-тестов, не этого шага).
Главное для шага 1 подтверждено: **jar собирается современным тулчейном
и headless-режим работает** — сборка готова к использованию как oracle.

2. **Ядро движка (Rust)** — событийный симулятор, встроенная библиотека

   `engine-cli`. Никакого UI — валидируется тестами и CLI.

   целиком; желательно иметь рано, чтобы дальше проверять фазы 2–6 на

3. **Editor Core (TS)** — сцена, canvas-рендер, размещение/wiring,

после того, как вокруг неё построен UI.

## 12. Безопасность

Разбираю по тем же двум слоям плагинов из §5, потому что у них принципиально
разный достижимый уровень доверия — общего решения "просто песочница" не
хватит на оба.

### Логические (WASM) плагины — сильная модель, потому что она дешёвая

Главный принцип: **минимизация импортов**. WASM-модуль по построению не
может ничего, чего ему явно не предоставили через imports — у него нет
амбиентных прав на файлы/сеть/DOM. Если ABI компонента — чистая функция
`eval(inputs, state) -> outputs, new_state` и хосту не нужно давать плагину
вообще никаких host-функций (или только безопасные: логирование,
детерминированный источник времени для симуляции), то песочница практически
герметична сама по себе, без доп. усилий:

- **Браузер**: хост (наш JS/TS bridge) сам решает, какой import-object
  давать при `WebAssembly.instantiate` — не давать доступ к DOM/`window`/
  сети. Компонентному плагину эти возможности и не нужны в принципе.
- **Native/CLI/Tauri**: инстанцировать плагины через `wasmtime` **без WASI**
  по умолчанию — тогда у модуля нет доступа к файловой системе/сети вообще.
  Если какому-то классу плагинов (например, плагин импорта/экспорта
  формата) реально нужен файловый доступ — WASI preview 2 с явным
  preopen конкретной директории (capability-based: доступ только к тому,
  что явно выдано, не ко всей ФС).
- **Лимиты ресурсов** — обязательны, т.к. память-safety ≠ защита от зависания
  или OOM: fuel/epoch-based прерывание в wasmtime (лимит на "шагов
  выполнения" за один вызов `eval`), верхняя граница на linear memory
  (`max_pages`). В браузере честного прерывания зависшего wasm-вызова из
  главного потока не бывает — поэтому недоверенные плагины стоит грузить в
  Worker (см. §3), откуда их можно `terminate()`, если `eval` не уложился в
  таймаут.
- **Детерминизм как побочный бонус**: тот же запрет на импорт "сырых"
  `Date.now()`/рандома, который снижает поверхность атаки, заодно защищает
  воспроизводимость симуляции (golden-тесты §7, повторяемые прогоны) —
  безопасность и корректность тут тянут в одну сторону, не конфликтуют.

### UI-плагины (JS/Vue) — слабая модель, надо явно это признать

Здесь всё наоборот: JS-плагин в контексте Vue-приложения по умолчанию имеет
полный доступ к DOM, `localStorage`, сети — то есть теоретически может
воровать данные открытого проекта или встраивать произвольный контент.
Полноценно изолировать это дорого (iframe с `postMessage`-протоколом, как у
VS Code webviews / Figma plugins) — для v1 закладываю **пониженную планку
доверия**, а не сэндбокс: грузим только явно установленные пользователем
UI-плагины, без автозагрузки из недоверенных источников, без "маркетплейса"
на старте. Изоляцию через iframe стоит держать в уме как путь роста, но не
делать блокером первой версии — иначе не сдвинемся с места ради риска,
которого пока нет (нет стороннего маркетплейса — нет стороннего кода).

### Файлы проектов, ссылающиеся на плагины

Если файл схемы (§9) может декларировать "для этого проекта нужен плагин X"
— нельзя тихо auto-load'ить и исполнять такой плагин при открытии файла,
полученного от кого-то другого. Нужен явный запрос подтверждения у
пользователя (по аналогии с "документ с макросами" в офисных пакетах),
особенно если плагин — из внешнего/незнакомого источника.

## 13. Установка плагинов без пересборки (drop-in файл в директорию)

Это возможно и нормально для native-таргетов, но именно **потому что мы
выбрали WASM**, а не потому что "любой плагин так можно". Стоит явно
проговорить, почему альтернатива была бы проблемой, и отдельно — что для
браузерной сборки "директория" не имеет прямого аналога.

### Почему WASM, а не нативная Rust-библиотека (dylib/`cdylib` + `dlopen`)

У Rust **нет стабильного ABI между версиями компилятора** — плагин,
собранный `rustc` другой версии, чем хост, при загрузке через `dlopen`
может не просто не заработать, а упасть с UB (несовпадение layout структур,
calling convention и т.п.). Это реальная и известная проблема нативных
Rust-плагинов "просто положи `.so`/`.dylib`/`.dll` в папку". WASM-модуль
таких проблем не создаёт: формат `.wasm` — сам по себе стабильный ABI,
интерпретируемый рантаймом (`wasmtime`), а не сырой машинный код с
compiler-specific layout. То есть решение "плагины через WASM" из §5 —
это не только про песочницу и переносимость в браузер, но и то, что вообще
делает "drop-in файл без пересборки хоста" безопасным и надёжным на native.
Если бы был выбран native dylib-подход, "просто добавить файл" был бы
хрупким и рискованным по умолчанию, а не просто "требует доп. работы".

### Native / CLI / Desktop (Tauri) — прямой fit

- Директория плагинов: `plugins/` рядом с исполняемым файлом или в
  стандартной пользовательской конфиг-директории (`~/.config/revlog/plugins`
  и аналоги на других ОС).
- Хост на старте (или по watch на директорию — для hot-reload в дев-режиме)
  сканирует `*.wasm`, инстанцирует через `wasmtime` с ограничениями из §12,
  без пересборки самого приложения — это штатный сценарий, не требует
  ничего специального сверх того, что уже спроектировано в §5/§6.

### Browser / Web — другая модель, нет "директории" как таковой

У браузера нет амбиентного доступа к произвольной директории на диске, так
что буквальный аналог "положил файл — плагин появился" не переносится
напрямую. Нужно отдельно спроектировать один из вариантов (или оба):

1. **Явный выбор файла пользователем** — `<input type=file>` /
   File System Access API (`showOpenFilePicker`), с явным consent-диалогом
   браузера. Чтобы плагин не терялся между сессиями — сохранять байты
   `.wasm` в IndexedDB и переинстанцировать при следующей загрузке
   (по-прежнему без сети/маркетплейса).
2. **Плагин по URL / хостед-реестр** — ближе к модели расширений браузера
   или marketplace; добавляет отдельный класс рисков (доверие к реестру,
   supply chain, нужны хеши/подписи) — это уже не то же самое, что "плагины
   на диске", и стоит явно решить, нужен ли такой реестр вообще для v1,
   или ограничиться (1).

Т.е. "установка без пересборки" — решённая проблема для desktop/CLI прямо
сейчас архитектурой из §5, но для web-сборки это отдельный нерешённый
UX/security вопрос, который стоит закрыть до реализации плагинного слоя
(фаза 5 в §10), а не постфактум.

### Манифест и версионирование ABI

Раз плагины собираются независимо и в разное время, хосту нужно понимать
совместимость **до** попытки вызвать неизвестный код:

- Плагин — самодостаточный `.wasm`-файл с метаданными **внутри** (custom
  section: id, semver плагина, версия `plugin-abi`, декларация нужных
  возможностей типа "нет"/"нужен файловый доступ", схема конфигурации для
  авто-генерации property-панели). Встраивать метаданные в сам wasm-модуль,
  а не в отдельный JSON рядом с ним по имени — меньше шансов, что
  пользователь при ручном drop-in занесёт файлы врозь или перепутает пару.
- `plugin-abi` (крейт из §8) версионируется по semver; хост при загрузке
  сверяет заявленную версию ABI и **отказывает с понятной ошибкой** при
  несовместимости мажорной версии, а не падает непредсказуемо. Это то же
  соображение, что и с Rust ABI выше, только на уровне нашего собственного
  контракта, а не компилятора.

## 14. Открытые вопросы / риски (нужно решение или проверка)

- **JS-логика в плагинах** (§5) — сознательно закрыл вопрос в пользу
  WASM-only для логики; если это неприемлемо (например, хочется учебных
  JS-скриптовых компонентов без компиляции) — это меняет архитектуру
  headless-запуска, стоит явно подтвердить или отвергнуть.
- **SharedArrayBuffer / COOP-COEP** (§3) — zero-copy обмен состоянием
  требует специфических HTTP-заголовков от хостинга; если деплой (например,
  GitHub Pages без контроля заголовков) это не позволяет — придётся
  оставаться на copy-based обмене через `postMessage`, что нормально, но
  чуть медленнее.
- **WebView-расхождения Tauri** (§6) — стоит рано прогнать canvas-рендер на
  WebView2/WebKit/GTK-WebKit, чтобы не упереться в баг рендеринга поздно.
- **Выбор native WASM-рантайма** (§12/§13) — `wasmtime` выглядит более
  очевидным выбором, чем `wasmer` (активнее развивается направление
  безопасности/метеринга, лучше документирован WASI preview 2) — но стоит
  подтвердить перед тем, как на нём завязывается плагинный слой.
- **Web-модель установки плагинов** (§13) — файловый пикер + IndexedDB
  против хостед-реестра, нужно решение до фазы 5.
- **UI-плагины и iframe-изоляция** (§12) — сознательно не делаю блокером v1,
  но если ожидается сторонний маркетплейс UI-плагинов раньше, чем кажется
  сейчас, изоляцию стоит планировать заранее, а не пристраивать задним
  числом.
- **Нужен ли экспорт обратно в `.circ`** (§9) — по умолчанию план считает,
  что не нужен (только импорт); если всё же нужен — это отдельная, не
  тривиальная симметричная задача (наш формат может выражать вещи, которых
  нет в `.circ`), стоит подтвердить сейчас, а не после того как всё
  спроектировано только "в одну сторону".
